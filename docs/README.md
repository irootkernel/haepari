Haepari is an independent Go CLI and local daemon for durable resource scheduling. Managed execution covers local commands and UTM macOS VM tests through one durable controller, capacity ledger, and fenced safe-return path. Cooperating tools, such as Mulgae reviews, can queue on advisory named locks. Public external leases are deferred. Aquarium is the first planned consumer; Haepari has no runtime dependency on Aquarium or its tools.

## Settled decisions

- Product and executable name: Haepari / `haepari`. Initial target: v0.1.0.
- Go core, CLI, transient runner, and local daemon; SQLite on a local filesystem.
- One controller per OS user and Haepari state root, with a private Unix socket. No public HTTP service.
- One named resource per managed Job. Different resources may run concurrently under one global occupancy limit; a UTM resource has capacity one.
- UTM uses managed execution for VM end-to-end tests (`make test-vm`), which run in the development loop; the owner expects 10–30 VM jobs a day. Local tests stay with each project and Gaori.
- Ordinary Mulgae reviews queue on the advisory lock `mulgae-review` and run when granted (ADR-0017). Locks grant no execution permit and count toward no managed capacity.
- License: MIT. Go module path: `github.com/irootkernel/haepari`.
- Linked external continuation is a deferred design with unresolved safety blockers.
- Managed admission, reservation, execution, collection, cleanup and return are distinct. Replay never launches a second uncertain workload.
- Project repositories own tests, installation recipes, migration fixtures, and hands-on checklists. There is no mandatory integration-test repository.
- `make test-vm` submits and awaits a job; guest execution uses a different entrypoint. UTM control belongs to the common adapter.
- An immutable consumer environment reference identifies selected profile bytes; rich validated installation combinations are optional consumer profiles. The consumer resolves aliases to immutable identities before submitting. Jobs never resolve moving `latest` references.
- Consumer-selected candidate deployment may cover binaries, skills, plugin resources and connection settings as opaque inputs; generic tests require no complete product installation unit. Binary and skill identities may differ where their native contract requires it.
- An optional consumer migration scenario creates state with the old version and preserves it while applying the candidate. Haepari never resets the VM; recipes set up and clean up their own state.
- Haepari schedules and records manual verification but does not infer a human pass or act as an LLM evaluator.
- Existing `aquarium-dev` state is retired through a staged consumer rollout, never by deleting its root before dependents are detached.
- The generic consumer contract freezes at gate F1 (managed core, TASK-012), gate F2 (VM fields, TASK-016) and gate F3 (consumer integration, TASK-020); TASK-002 is provisional. The [F3 decision](records/TASK-020-consumer-freeze.md) defines the implemented surface and takes effect with canonical TASK-020 acceptance.
- The macOS controller runs as a `gui/<uid>` LaunchAgent in the Aqua session with `AbandonProcessGroup=true`; runners use their own session; darwin SQLite uses `fullfsync` and `checkpoint_fullfsync`. No signing identity is required: an ad-hoc-signed LaunchAgent controls UTM through `utmctl` without an Automation prompt (TASK-034).
- Each `utm-macos` resource is one persistent VM that Haepari never clones or resets (ADR-0018); the guest runner travels with each job. `host_macos_guest_limit` bounds registered running and pending/uncertain starts. Automatic capacity-driven stop requires explicit operator permission on an eligible resource, and pause protects maintenance.

## Document authority

Requirements own product obligations. The architecture and active managed contracts own implementation semantics. ADRs own rationale. The roadmap alone owns Haepari task identity, sequence, and lifecycle status. Task checkboxes are implementation acceptance evidence, not independent lifecycle records.

The Aquarium repository's `docs/roadmap/README.md` owns Aquarium IDs and status. The adoption copy in this package is a handoff aid, not a second roadmap authority. The planned Aquarium epic is Aquarium:EPIC-019, with Aquarium:TASK-086 through Aquarium:TASK-102. Inside this package an unqualified EPIC or TASK ID is a Haepari ID; an ID from another repository is always qualified, as in Aquarium:TASK-092. [External requests](to-external.md) lists requested changes to other repositories; it is not their authority.

The templates in `docs/examples/` are illustrative design fixtures, not working scripts or production-ready configuration. The runnable reference caller is [examples/project-test](../examples/project-test/README.md). Placeholder identities must be rejected by the implemented validators. No real credentials or current private runtime data are included.

External facts are identified in [sources](sources.md). Architecture choices and acceptance criteria remain target contracts; the implemented slices are described above, and the canonical roadmap records their lifecycle states. The package preserves the user's settled direction; any later material scope change needs a recorded decision.

Documentation check results are recorded in [package validation](package-validation.md) and reproducible with `docs/tools/validate_docs.py`. The Aquarium-owned inspector warning is tracked in [external requests](to-external.md) §1.3.

Follow-up candidates from EPIC-001 cold validation and EPIC-002 task reviews, and the adopted EPIC-009 execution dossier, are indexed in [TODO](TODO.md). The dossier integrates execution requirements and links canonical product owners; neither it nor the TODO index owns roadmap lifecycle. At approved closeout, promote durable outcomes before removing a temporary dossier and replacing its links.

[Deferred feedback](deferred-feedback.md) owns small postponed follow-up checks and their re-entry conditions. It preserves the original TASK-016 waivers and current unobserved limits; Design Revision 3.5 reclassifies DF-001–004 as optional hardening with no first-release deadline. The roadmap remains the sole lifecycle authority.

The [TASK-016 VM freeze decision](records/TASK-016-vm-contract-freeze.md) defines the candidate F2 field boundary, qualification scope and deferred checks. It becomes effective only with canonical TASK-016 acceptance.

The [Mulgae integration contract](integrations/mulgae-review.md) defines the managed VM adoption boundary and how ordinary reviews queue on the advisory lock. It is planned downstream behavior, not a Haepari dependency or a claim about the installed Mulgae release.
