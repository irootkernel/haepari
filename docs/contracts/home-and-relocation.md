# Home roles and installation-preserving relocation

Selected v0.1.1 contract for TASK-040, explained by [ADR-0023](../architecture-decision-records/0023-home-separation-and-relocation.md). TASK-042 implements release-service plan v2 and default-home support. Relocation remains planned TASK-043 work; TASK-044 qualifies the exact packaged candidate. The [roadmap](../roadmap.md) alone owns acceptance.

## Home roles and compatibility

The native default remains `~/.haepari/`. Root selection stays explicit CLI root, then `HAEPARI_HOME`, then that default; a configuration file never selects another root. Haepari development uses an independent, initially empty `~/.haepari-dev/`, instance `main`, and initial limits 1/1. Shared consumption keeps its explicitly selected existing installation until the later Aquarium adoption operation. A directory's name does not select its service family or make it disposable. Do not copy the shared database, change global shell/MCP selection, or overwrite a running candidate binary.

New `service plan --release` responses select `haepari.release-service-plan/v2`, for both default and non-default roots. Its closed fields remain `schema`, `instance`, `label`, `domain`, `owner_uid`, `binary`, `binary_sha256`, `root`, `plist_path`, `plist`, `global_limit`, and `host_macos_guest_limit`. Limits remain explicit positive global and host 1 or 2, defaulting to 1/1. Label remains `io.rootkernel.haepari.<instance>`; the owner marker remains `.development-service.json` with `haepari.release-service-owner/v1`. The filename is historical, not a development-family permission.

Release v2 permits the resolved native default; private-path, exact executable digest, owner, Aqua domain, plist and state-preserving install/uninstall fences remain mandatory. Development v1/v2 still reject the default. Reading or recreating a non-default release v1 plan uses its original schema and bytes, not the new planning default. Historical release v1 default plans remain invalid. Install revalidates the executable bytes and complete saved plan. Uninstall retains the existing ability to remove an exact owned service when its executable has changed or disappeared: it validates the saved plan's root, owner/domain/label and pinned plist location, and the actual owned plist, without hashing the executable. Release v2 also checks the saved plist against its serialized fields. An unrelated unsafe default directory does not block removal of a valid non-default service. New fields, duplicate keys and unknown versions refuse; there is no implicit plan upgrade. Existing help output receives append-only command/schema additions under the recorded freeze-delta rule, without changing earlier entries or wire schemas.

## Relocation surface

```text
haepari service relocate plan --source-plan <source-service-plan> --target-plan <target-service-plan> --backup-dir <absolute-private-backup-directory> --json
haepari service relocate apply --plan-file <relocation-plan> --json
haepari service relocate status --plan-file <relocation-plan> --json
haepari service relocate rollback --plan-file <relocation-plan> --json
```

All four use the existing `haepari.envelope/v1`, operation `service.relocate.<action>`, and existing error/exit semantics. Plan files contain the response `data` object, not the envelope. Unknown/irrelevant flags refuse before effects. None bootstraps, boots out or rewrites a service plist, starts a daemon, signals a workload, changes resources, performs evidence disposal, or edits consumer configuration. Service removal and later target installation are separate operations through their exact saved plans.

Supported pairs are release v1 or v2 source and release v2 target, with the same owner UID, instance, label, domain and plist path. Only roots, executable selection/digest and the resulting root/binary-dependent plist bytes may differ; both limits must match. A changed binary is an explicitly pinned forward upgrade, not permission to mutate that file. The mover runs from the exact target-plan binary; both original and target executable files must remain present, outside both moving roots and the backup tree, and match their digests throughout the operation. Development-family relocation, service-family conversion and relabeling are unsupported. A release installation in a dev-named directory remains eligible.

## Plan v1

Planning reads without creating roots, lockfiles, backup directories, journals, SQLite migrations, checkpoints or service effects. In particular it does not use the ordinary create/migrate SQLite opener. It emits closed `haepari.service-relocation-plan/v1` only from an already stopped, owned source whose logical database can be read consistently. An existing controller lockfile is opened without creation and held exclusively during observation. Release that observation lock after planning; the output is not a reservation.

The plan has these required fields:

| Field | Binding |
| --- | --- |
| `schema`, `relocation_id` | Exact schema and one fresh lowercase 32-hex identity, reused for every attempt with this plan. |
| `installation_id` | Original persisted installation identity, never derived from the target path. |
| `source_plan`, `target_plan` | Complete strictly decoded saved service plan objects; their exact canonical digests bind the selected versions. |
| `source_root_identity`, `source_parent_identity`, `target_parent_identity`, `backup_parent_identity` | Records with `identity`, `owner_uid` and `mode` for each existing directory, observed through its descriptor. |
| `backup_dir` | Absent absolute private destination outside and non-overlapping with both roots; parent must already exist. |
| `files` | Complete sorted source-relative inventory, including directories, DB/WAL/SHM when present, objects, Job files, root owner and controller lock. |
| `ledger_sha256` | Digest of the complete deterministic logical database inventory, including schema identities, all tables/columns/rows and stored payload bytes. |
| `plan_sha256` | Digest of canonical plan JSON with only this field omitted. |

The only optional plan field is `predecessor`, required when a current terminal journal exists. It binds that journal's `relocation_id`, `plan_sha256`, `sequence`, exact raw `journal_sha256`, descriptor-observed `journal_identity`, and `current_root`. It is absent for the first relocation. A nonterminal predecessor refuses new planning; a terminal predecessor is eligible only at its recorded current root with the same installation and matching current service owner. A new plan pins the current stopped ledger and inventory, including any work completed since the predecessor; it does not reopen the predecessor's rollback authority.

Canonical JSON and SHA-256 follow the existing managed canonicalization rules; digests use `sha256:` plus 64 lowercase hex digits. File entries have `path`, `kind`, `identity`, `owner_uid`, and `mode`; regular files also have `size` and `sha256`. Paths are unique normalized relative paths with no traversal or case-fold collision. Identity records reuse descriptor-observed volume UUID, 64-bit file ID and creation seconds/nanoseconds from [prepared identity](../architecture-decision-records/0022-prepared-identity-and-scoped-recollection.md), plus same-boot device/inode checks. Directory identities exclude mutable size/link-count/mtime from equality. Missing persistent identity support refuses.

Inventory excludes no retained history. Unknown files remain inventoried regular files, never deletion candidates; unknown links, hard links, device nodes and FIFOs refuse. The one recognized private `control.sock` may be inventoried as a socket only with the service stopped, exclusive controller lock and no live listener. It has no copied backup payload and stays present in the renamed root for ordinary proven stale-socket handling. Plan does not unlink it. A pre-existing nonterminal relocation journal is handled only by its exact plan. A terminal journal can be the explicitly bound predecessor of a new plan through the succession protocol below; it is never silently overwritten or treated as absent.

The logical inventory sorts schema definitions by table name and includes their original SQL and ordered column declarations. Each row encodes every column as its SQLite storage class plus original integer/text/blob bytes (a real value uses its exact IEEE-754 bits); rows are byte-sorted within each table with duplicate rows retained. Length-delimited canonical entries prevent delimiter ambiguity. All DB rows are compared without changing their saved JSON, digests or clocks. `ledger_sha256` is an inventory binding, not a replacement for native result/receipt validation. Schema layouts not supported by the target binary, absent required tables/identity, corrupt or unreadable evidence inventories, and unrecognized durable control state refuse before mutation. No token expiry or fresh plan silently renews a saved Job deadline.

## Eligibility and exclusive apply

Apply rechecks the entire plan, both binaries, directory identities and inventories after acquiring the original `controller.lock` exclusively without unlink/replacement. Keep that descriptor held across rename, journal updates and completion. Also exclude concurrent seal/store effects through their existing ownership lock. Both service identities must be observed unloaded and their exact plist absent; mere socket unreachability is not proof. The source root must still be the planned directory and the target still absent, on the same local volume with an already existing verified parent. Paths must not alias, nest, traverse links or overlap the backup.

Read the ledger offline and refuse every queued/active/reconciling managed Job, occupied lease, queued/unclaimed/current advisory grant, unresolved recovery/retention/staging/purge intent, pending native effect, unknown occupancy, unfinished cleanup, or live owner. Ended histories may be retained. A terminal FAIL or INCOMPLETE alone does not block: its unresolved protected evidence or uncertain cleanup does. A missing-evidence terminal history with no outstanding hold remains a gap, not a repaired result. Do not force-release, cancel, dispose or edit SQL to make an installation eligible.

Root-local immutable references remain historical. Moving a completed local runner request does not retarget it, authorize `runner start`, or reset replay. Root-relative retained host artifacts and logs are opened through the current verified root with their original file identities. Guest roots, registrations and SSH identities do not change. A live external resource/runner/configuration reference into the old root, an external config file that the target service cannot select identically, or a reference whose ownership/classification is unknown blocks apply; its supported owner must resolve it first. The mover never performs a blanket string replacement or creates a compatibility symlink.

## Terminal journal history and succession

Keep the current journal at `.service-relocation.json` and immutable terminal snapshots under the private root-local `.service-relocation-history/` directory. Each snapshot name is `<relocation_id>-<journal_sha256-hex>.json` and contains the exact terminal journal bytes, including its original plan and receipts. Snapshot contents and existing history files are never rewritten or removed by relocation. New history directory creation requires no-follow private owner validation and parent sync; an existing directory must pass those same guards. Existing history entries must match their name, closed journal schema and installation; unrecognized or conflicting entries refuse rather than being cleaned up.

Only a new plan's apply may succeed the current terminal journal. Under the original controller/store locks, revalidate its exact `predecessor` identity, bytes, sequence, terminal phase, installation, current owner/root and the new plan's complete source inventory. First publish the predecessor snapshot without replacement, sync it and its directory, and verify the exact bytes again. Publication uses the outside-root staging protocol below followed by no-replace rename, never a partially written final snapshot. If a crash left the final snapshot present before successor publication, accept it only when its private regular-file guards and complete bytes equal the still-current, independently verified predecessor; this is idempotent copying of known terminal metadata, not adoption of another plan or evidence. An unexpected/partial final snapshot conflicts. Unpublished sibling staging leftovers are preserved and do not count as a published snapshot.

Then publish the new prepared journal by atomic replacement of the exact current predecessor and sync the root. Its `predecessor_archive` records the snapshot's relative `path`, persistent file `identity`, `sha256`, and the history directory's `directory_identity`, `owner_uid` and `mode`; bind these observations before replacing the predecessor. Recheck the predecessor immediately before replacement while holding its verified root and the operation locks. The complete successor journal, its original plan and its archived predecessor must be durable before any backup-directory creation. A crash before this replacement leaves the predecessor current and can repeat the same snapshot step; a crash after it resumes only the exact successor. Do not perform a separate destructive archive/delete of the active journal.

No concurrent successor can win through a changed predecessor: plan/source-inventory drift conflicts. Once a successor is current, old-plan apply and rollback refuse even if an archived receipt says complete; they never modify the successor or replay a move. Old-plan status may read its immutable snapshot and return its stored terminal receipt when the same installation and identity-bound snapshot are reachable at one of that old plan's two roots. Resolve it by following the current journal's verified `predecessor_archive` chain until the requested relocation ID and plan digest match; reject missing, replaced, conflicting or cyclic links, and never select a snapshot by filename prefix alone. If neither old location contains it after a later move, status reports the ordinary conflict/unavailable observation; it does not search other homes or recreate history. The snapshots move with the same installation for supported current-root inspection.

## Atomic publication without root-local temporary files

Journal, terminal-snapshot and owner-marker publication must never create a temporary file inside either installation root or its history directory. Before each publication, create a fresh exclusive mode-0700 attempt directory beneath the already verified parent of the current installation root, outside both moving roots and the backup payload. Match that parent to the applicable `source_parent_identity` or `target_parent_identity` in the exact plan, according to the verified current root. Require the held parent, attempt directory and destination descriptors to report the same local volume/filesystem; if those observations cannot be established, refuse before publication. Its unpredictable name is collision avoidance, never ownership evidence. No plan or journal field claims durable ownership of this staging directory.

The creating process holds no-follow descriptors for the verified parent, new attempt directory and exclusive private staging file. Validate their owner, type, link count, persistent identity and unchanged descriptor/path relationship before writing and again before publication. Write the complete intended record, verify its exact bytes/digest, and sync the file. Only then rename that held staged file descriptor-relatively into the verified current root/history directory: no-replace for initial journal or immutable snapshot publication, exact-current-record replacement for a guarded journal/owner update. Recheck the destination's required absence or exact current identity/bytes under the original operation locks immediately before rename, then sync the destination directory and staging directory. Once published, the new object is governed by the ordinary journal/history/owner-marker inventory and identity rules. Never recover a publication from a staging filename or partial content.

After a process interruption before publication, the complete installation inventory and last durable record remain unchanged; the incomplete file is a sibling outside that inventory. A new process neither opens it as an owned input nor adopts, deletes, renames or bypasses a destination fence because of it. It creates a different fresh exclusive attempt directory and derives the next record from the still-current durable journal and actual root/ledger/history identities. Thus same-plan apply or rollback remains available without a second journal recording temporary-file ownership, and a partial staging file cannot strand a nonterminal relocation. An interruption after rename follows the ordinary actual-record/phase reconciliation and never assumes the previous staging file still exists.

The live creator removes only its own staging file/directory while its original descriptors still prove identity and no publication uses them. A failed cleanup or lost-creator directory stays retained for its separately authorized operator/fixture owner; later attempts never sweep siblings or infer ownership from a prefix. Existing unrelated or abandoned siblings remain outside Haepari's installation inventory and untouched; their presence alone is neither a startup nor relocation blocker and they are never included as backup data. Plan and status create no staging. The same publication rule applies to the backup manifest, using the exact plan's verified `backup_parent_identity` for same-filesystem staging outside the bound backup directory; no final manifest can be a partially written staging file.

## Backup and durable journal

After revalidation, first publish and sync a private prepared `.service-relocation.json` in the moving root, using the predecessor protocol when applicable. The journal is closed `haepari.service-relocation-journal/v1`, binding the full original plan, `plan_sha256`, monotonic `sequence`, `phase`, `activated` (initially false), `backup_state` (initially `not_created`), and the exact original/target owner-marker bytes. Optional fields are `predecessor_archive` for a successor, `backup_identity` after the created backup directory is durably bound, `backup_manifest_sha256` after backup verification, `completion_receipt` after successful apply and `rollback_receipt` after successful reverse move; receipts use the shape below. `backup_identity` is the same directory record shape (`identity`, `owner_uid`, `mode`) used by the plan's parent bindings. No other fields are admitted. A nonterminal journal cannot be overwritten by another plan. Publish each next complete record through the outside-root staging protocol, atomic replacement and directory sync; partial bytes never enter the installation inventory.

Only after the prepared journal is durable may apply exclusively create `backup_dir` beneath its verified parent. Open the new directory without following links, verify private owner/mode and persistent identity, sync the new directory and parent, then persist that exact `backup_identity` and `backup_state=bound` in the journal before copying any payload. This binding is not atomic with mkdir: an interruption can leave a directory without a durable identity binding. If the plan's backup path exists while the durable journal has no `backup_identity`, status reports `backup_state=unproven` and apply refuses to adopt, inspect as owned, copy into, delete or reuse it, even if empty or carrying a plausible plan prefix. Preserve it; it is not a verified backup. If the path is still absent, exact same-plan apply may perform the original exclusive creation. Once the binding is durable, every continued backup write and manifest publication rechecks the parent and bound directory identities; replacements refuse.

For the unproven pre-binding case, the supported bounded recovery is same-plan rollback before any root move: verify the original source root, marker, retained inventory and logical ledger are unchanged apart from this operation's declared metadata, then publish `rolled_back` with `backup_state=unproven`. It settles only this relocation's source-side attempt and leaves the unproven external path untouched for its separate operator/owner; the receipt makes no successful backup or directory-ownership claim. A later new plan may use a different absent backup destination through terminal-journal succession. No flag or retry may promote the old unproven directory to owned state. If the source cannot be verified unchanged, rollback also refuses and preserves the current journal.

Revalidation never excludes the whole metadata namespace. Compare the original complete installation inventory, accounting only for this exact operation's published current journal version, its recorded owner-marker bytes, the exact predecessor snapshot and any history directory created by the declared succession. There is no root-local temporary-file exception: unexpected files inside the installation/history still refuse, whether complete or partial. Sibling staging is outside the installation tree by construction, not omitted from a tree that contains it; a continuation neither reads it as evidence nor treats it as authority to alter the plan. Each published metadata object must pass its declared owner/type/content and, once bound, identity checks; bind retained history identity in the successor before any move. Unrelated additions, replacement or altered earlier history refuse. A continuation cannot change its plan's original inventory to hide drift. Predecessor snapshots and declared journal replacements are lifecycle metadata changes, not edits to historical Job payloads or ledger rows.

Backup retains canonical copies of the complete original source/target plan objects and the verified executable bytes, the full retained regular-file tree, directory metadata and a SQLite backup produced from a read-only consistent source transaction including committed WAL state. Verify the backup DB's integrity and complete logical inventory against `ledger_sha256`, and every copied payload against its planned digest. Retain original DB/WAL/SHM bytes separately when present. Publish a complete manifest last with exclusive creation and sync files, directories and backup parent, then record `backup_state=verified` and its digest in the journal. A partial backup is never a verified restore point. Same-plan continuation may finish only its durably identity-bound partial backup; it never merges an unrelated directory or accepts an existing unowned manifest.

| Durable phase | Next permitted effect and reconciliation |
| --- | --- |
| `prepared` | Create and durably bind the backup directory before copying; resume only a bound directory. A present unbound directory requires conservative refusal or the verified pre-move rollback above. No rename before backup verification is durable. |
| `backup_verified` | Revalidate source/parents/target, persist `rename_pending`, and sync before rename. |
| `rename_pending` | Use descriptor-relative no-replace directory rename. After uncertainty, identify the original root at source or target; continue only when exactly one matches. Sync both parents. |
| `moved` | Verify unchanged retained identities and logical history, persist `owner_pending`, then replace only the root owner marker's `root` field with the target path. |
| `owner_pending` | Accept only the saved original or exact intended marker; finish that replacement, sync and verify the final inventory. |
| `complete` | Return the stored completion receipt. No service start or consumer resumption is implied. |
| `rollback_pending` | Reconcile the reverse no-replace rename and exact owner-marker restoration under the same identity guards. |
| `rolled_back` | Return the stored rollback receipt; a later forward move needs a new plan bound to this terminal predecessor and the succession protocol. |

Every phase boundary is persisted before the described external effect; completion follows verified effect and required syncs. Crash after effect but before phase publication is resolved from actual identities, not from the last phase alone. Before the first rename, rollback can settle the original source without deleting its backup. After rename, rollback first persists its intent, restores the original marker as appropriate to the observed root and reverses the move without replacement. It preserves the journal, receipts and backup. Neither direction unlinks a foreign/replaced target to make room.

Ordinary daemon startup refuses a nonterminal relocation journal before opening/migrating SQLite, repairing the socket or dispatching. A terminal journal permits startup only at its recorded current root with the matching installation and owner. Old binaries without this guard must remain unloaded during relocation; the kernel lock alone cannot constrain an unsupported binary after the mover exits. Supported target startup holds the original controller lock, revalidates the terminal journal and publishes `activated=true` with the next sequence using the same synced atomic journal replacement before normal database opening. A later startup that observes `activated=true` does not rewrite that fact or create a new relocation receipt. Activation grants no rollback after new work.

## Status, replay, errors and rollback limits

Status is observation-only: no backup repair, phase advance, lockfile creation, SQLite migration, schema repair or service effect. It checks both possible root locations with no-follow identities and returns `haepari.service-relocation-receipt/v1`: `schema`, `relocation_id`, `plan_sha256`, `installation_id`, `phase`, `sequence`, `source_root`, `target_root`, `current_root`, `backup_state`, and `backup_manifest_sha256` (omitted until verified). `backup_state` is `not_created`, `unproven`, `bound` or `verified`; absence of a durable binding never reports bound/verified. Before apply it may report `planned` with sequence zero and `not_created` after validating the unchanged plan, including its predecessor when present; this creates no journal. This observation is not apply permission. Durable successful apply/rollback receipts use the same shape with `complete`/`rolled_back` and are retained in the journal; identical completed apply returns its stored receipt only while that plan remains current and current identities remain valid. Apply after rollback or succession conflicts. Any uncertain response is recovered through this same plan and status, never an invented relocation identity.

Use existing machine classifications: malformed/unsupported input is `INVALID_REQUEST`; changed plan, binary, identity, destination or competing plan is `CONFLICT`; proven occupied/unresolved lifecycle is `RECOVERY_BLOCKED`; I/O, durability or unavailable observations remain `STORAGE_UNAVAILABLE` with `retry=reconcile`. Invalid input/conflict use `retry=none`. Preserve source, backup and journal on failure. Refusal names the fixed validation stage and safe cause, not raw SQLite content, credentials or arbitrary filesystem/backend errors. Existing envelope exits remain authoritative; no successful receipt is emitted before final verification.

Rollback requires both services still stopped, consumers not resumed, matching journal and original files, source destination absent when reversal is needed, and no new Job, grant, mutation or changed logical history since apply. Reopening the target is not permission to downgrade: if a forward upgrade or any later work changed the bound logical inventory, rollback refuses. Even where startup left that inventory unchanged and rollback is possible, use the supported v0.1.1 binary at the original root; no schema downgrade or old-executable restoration is automatic. A copied backup has different file identities and is not a runnable restoration claim. Never restore it over newer work. Backup deletion requires a separate owner decision.
