# CLI and job contract

Contract family: `haepari.* / v1`. Proposed public surface for v0.1.0. TASK-002 defines provisional schemas and examples; local and failure evidence refines them. Freeze gate F1 (TASK-012) freezes the managed core contract and machine-readable help, gate F2 (TASK-016) the VM fields, and gate F3 (TASK-020) the generic consumer integration contract (wrapper, guest entrypoint, immutable environment reference and general manual results). See the [roadmap freeze gates](../roadmap.md#contract-freeze-gates). The [F3 decision](../records/TASK-020-consumer-freeze.md) records the implemented consumer surface; it becomes effective with canonical TASK-020 acceptance.

This contract describes managed Jobs. TASK-033 implements `resource register`, `submit`, `run`, `inspect`, and `wait` for a single capacity-one local auto-Job resource. Queued input loss and queue expiry settle INCOMPLETE without a lease; incomplete output collection retains the owned workspace and quarantines the resource. TASK-007 extends local registration to multiple resources and configured capacities, enforces per-resource FIFO and the controller's current global limit, and implements `resource inspect` plus fenced `resource pause`/`resume` with JSON output. These commands interpret `--expected-revision` as the availability revision and optionally accept `--request-key`. Omitting the key generates a fresh random mutation identity for that invocation; supply and persist an explicit key for exact replay after an uncertain reply. `--reason` applies to pause and must contain 1–256 bytes (default `operator_pause`); resume rejects that flag. Read the current fences with `resource inspect <id> --json`. By default each invocation observes the current configuration/lease epoch. For exact CLI replay across intervening reservations or configuration changes, persist the key and explicitly supply both `--expected-config-revision` and `--expected-lease-generation` from the first observation, with the original availability revision. Explicit configuration revisions must be at least 1 and lease generations at least 0; supplying only one pin or an invalid explicit value is rejected before connection or mutation. Repeat those identical flags after an uncertain reply. A changed epoch in a new request under the same key remains `CONFLICT`; the replay path does not weaken any fence or apply the mutation twice. A local resume records controller-observed filesystem readiness and cannot clear quarantine. An exact committed resume replay returns the stored mutation identity and current resource state without taking a new readiness observation. The observation records facts at its stated observation time; it does not lock filesystem state through the SQLite commit. An omitted `idle_since` means the historical idle time is unknown. The configuration digest returned by resource inspect is the SHA-256 of the canonical stored registration JSON. The resume readiness reference contains the installation, resource, relative jobs path, permission mode, modification and observation times, outcome and fresh reference; its SHA-256 digest binds those exact recorded facts. Pause clears client-supplied readiness fields. Quarantine changes are also published to sibling queued Jobs as availability events. TASK-037 exposes a positive controller startup `--global-limit`, default 1, separately from the host macOS guest limit; the general configuration loader remains TASK-023. TASK-013 connects UUID/pin-verified VM registration and fenced idle VM updates to the public controller. Host guards and power-intent reconciliation remain internal adapter APIs. TASK-015 implements automatic development VM Job admission, readiness-verified VM resume and revision-bound Job/resource recovery; VM resource removal remains unsupported. Registration uses read-only `utmctl list` and performs no power effect. A VM update requires `--expected-revision` (configuration) and `--expected-availability-revision`, plus successor configuration revision; it preserves maintenance availability and refuses occupied or power-protected resources. TASK-008 implements bounded `jobs list`/`resources list`, `events`, `logs` and `cancel`, protocol range negotiation, and commit-driven observers. TASK-019 implements `manual complete` for local and development VM Jobs, keeping native preparation separate from recorded human observations. VM resource removal and release commands remain unsupported. External requests are a [deferred design](external-leases.md), not a v0.1.0 CLI family. Do not use `manual` Jobs to emulate external execution.

| `haepari job recover <job-id> --plan [--action reconcile\|attest-stopped\|attest-no-start] --json` | Read-only exact run, resource generation, receipts, unknowns and proposed reconciliation path. Scoped operator actions require attested evidence when applied. |
| `haepari job recover <job-id> --plan-token <token> --request-key <key> [--evidence-file <json>] --json` | Fenced local recovery mutation; cannot declare unknown execution stopped without machine proof or scoped operator attestation. Attestation never yields PASS. |
| `haepari purge <job-id> --expected-revision <n>` | Remove a finished job's unprotected bulk data; refuse deletion of evidence reachable from unresolved retention/recovery references and keep a request-key tombstone. |

A mutating command is an explicit user/agent action within the established authorization scope. Ordinary offline submit/wait/reconnect/cancel/owned cleanup may reuse an approved development scope; candidate changes do not require per-Job approval files or repeated questions. Capture actual input/executable/result identities automatically. Registration alone is not workload authority; see [ADR-0020](../architecture-decision-records/0020-local-development-scope.md). The paired skill must carry the actual authorization context and scope. Merely having the CLI, an existing job, or an inbox item is not authorization to install, execute providers, reset foreign state, or publish a release.

The base recovery plan schema is `haepari.recovery-plan/v1`. TASK-036's cross-boot and pre-guest power-boundary paths emit `haepari.recovery-plan/v2`; orphaned power intents use the separate `haepari.power-recovery-plan/v2`. `snapshot` binds installation, Job/resource/configuration/lease/run fences, durable phase and runner facts, adapter identity/state/stage and retained results as applicable. `observation`, `observed_at`, `unknowns`, `proposed_effects` and `evidence_loss` describe the current proof and gaps. A supported action returns `plan_token` and `expires_at`; a blocked or unimplemented backend path returns no token. Unapplied tokens expire after two minutes, bind both the ledger snapshot and native observation digest, and are invalidated by controller restart. They are cooperative fences, not same-user OS security boundaries.

Applying requires a saved request key (at most 100 bytes for Job recovery, 90 for resource recovery). An identical committed token/key/evidence request returns the original mutation identity before current expiry or lease checks; a changed payload under that key conflicts. Job replay returns its original receipt; resource replay also observes current availability without executing another recovery. Operator evidence is a closed object with `source=operator-attested`, nonempty bounded `observer`, UTC `observed_at`, `mechanism`, `digest` (`sha256:<64 lowercase hex>`) and `reference`. Only explicitly planned attestation actions accept it. A positively observed matching live execution or incomplete filesystem owner contradicts termination attestation: the plan returns no token and apply refuses before importing receipts or committing recovery intent. A consistent terminal proof may be consumed even while its supervisor finishes publishing receipts. Recovery intent binds that evidence to the exact Job/run/lease, keeps provenance across restart, and cannot upgrade an immutable terminal verdict or produce PASS from attestation.

TASK-009 runner operations emit `haepari.envelope/v1` with operation `runner.<operation>` after accepting the command syntax and required `--request` argument. Successful responses contain receipt observation data (`state`, optional `intent`, `start`, `outcome`, `exit`); failures contain the machine error described below. Malformed usage, including an unknown operation or flag, a missing `--request` argument or an extra positional argument, prints usage to stderr and exits 2 without a JSON envelope. A supplied request path that fails semantic validation still produces an error envelope. The optional `--json` flag is accepted for CLI call-site uniformity and does not change the output format. `inspect` reads only; `watch` observes the same request with a finite budget derived from remaining run time, termination time and up to one second of observation slack; `cancel` writes a durable exact-request intent. Start returns the existing active/completed run or refuses ambiguous intent; it never admits a Job or replays an uncertain workload. Conflicting/invalid input exits 2, unresolved termination or spawn returns `RECOVERY_BLOCKED` with exit 2 and `retry=reconcile`, and storage/observation failure exits 6. Success reports receipt availability, not a Job verdict. The gated `_exec` trampoline is internal and requires inherited supervisor pipe descriptors; it is not an operator execution interface. See [runner receipts](resource-and-runner.md#runner-receipts).

## JSON envelopes and exit codes

Every JSON response is one closed object with `schema`, `operation`, `ok`, and either `data` or `error`. Errors include a stable `code`, a bounded explanation, a retry/reconciliation classification, and an optional job/resource reference. Never embed secrets or unrestricted child stderr.

The provisional internal envelope identifier is `haepari.envelope/v1`. `ok=true` requires `data`; `ok=false` requires `error` with exactly one of `none`, `retry_same_key` or `reconcile` as its retry classification. Both branches reject unknown top-level fields and duplicate keys. Public input documents also reject unresolved placeholders; response data may contain literal angle brackets in workload output. Nested operation-specific `data` is validated by that operation's schema before use.

| CLI exit | Meaning |
| --- | --- |
| 0 | Command succeeded; for `run`/terminal `wait`, final verdict PASS. |
| 1 | Terminal `run`/`wait` has a verified FAIL. |
| 2 | Invalid usage, rejected input, conflict, unsupported contract, or a known admission whose retained result is unavailable. No implied workload failure. |
| 3 | Terminal INCOMPLETE with a known result envelope. |
| 4 | Terminal job is CANCELLED after safe settlement. |
| 5 | Caller wait deadline elapsed; the job is not cancelled. |
| 6 | Transport outcome uncertain or controller unavailable; reconcile the same request key before another submit. |

Each machine error code maps to one CLI exit:

| Error code | Meaning | CLI exit |
| --- | --- | --- |
| `INVALID_REQUEST` | Malformed, unsafe or placeholder input | 2 |
| `CONFLICT` | Different submitted digest under an existing key; changed surviving input or invalid inventory on replay; changed input during sealing or declared/sealed inventory mismatch before admission (no key consumed); or conflicting mutation replay | 2 |
| `UNSUPPORTED` | Unsupported mode, schema version, platform or backend, including external execution | 2 |
| `PREREQUISITE_UNAVAILABLE` | An input or backend prerequisite is unavailable, including VM UUID/pin verification at registration or update; for Job admission, no admission or key consumption occurs | 2 |
| `NESTED_ACQUISITION_REJECTED` | Submission (including `run` admission) or advisory lock acquisition from a caller whose parent context occupies capacity | 2 |
| `NESTED_WAIT_REJECTED` | Blocking observation (`wait`, `events --follow`, `logs --follow`) of a non-terminal job from such a caller | 2 |
| `NOT_FOUND` | The job, resource or recovery plan does not exist | 2 |
| `RESULT_UNAVAILABLE` | The admission is known but its retained result is unavailable; no new job is launched | 2 |
| `RESOURCE_BUSY` | The resource change requires an idle or unreferenced resource | 2 |
| `LOCK_EXPIRED` | A lock grant expired or was released before this renewal | 2 |
| `PROTOCOL_UNSUPPORTED` | CLI and controller share no protocol version; no mutation | 2 |
| `STALE_REVISION` | The expected revision is no longer current | 2 |
| `RECOVERY_BLOCKED` | Recovery or pause/resume refused, or manual completion not prepared, retired, deadline-expired or lacking verified preparation; inspect the operation-specific message | 2 |
| `WAIT_TIMEOUT` | The caller's wait deadline elapsed; the job continues | 5 |
| `TRANSPORT_UNCERTAIN` | Controller unavailable or reply lost; reconcile the same request key | 6 |
| `STORAGE_UNAVAILABLE` | The controller could not safely read or commit durable state; a failed mutation is not acknowledged | 6 |

TASK-023 M2b-2 F1 does not change this exit table. F2 keeps these `clientFailure` exits and adds no exit 3 or 4.

`inspect`, `events`, and `logs` return 0 when their own read succeeds, regardless of workload verdict. Preserve a native command's exact exit code/signal inside the run result; do not substitute it for the CLI operation code. `run --json` may stream versioned admission/event/final objects as NDJSON, while ordinary command responses remain one JSON object. The schema must distinguish those modes.

In the TASK-033 local slice, `run` waits for at most 24 hours after admission, and each `wait` call accepts at most a 24-hour timeout. A caller wait deadline returns exit 5 while the Job continues; use its printed Job ID to wait again. This bound is separate from the admitted Job's run deadline.

## Job input

`haepari.job/v1` contains the following closed fields (the example is provisional until freeze gate F1, and its VM-specific fields until F2):

- `schema`: exactly `haepari.job/v1`.
- `execution_mode`: exactly `managed`; the selected resource must admit managed execution.
- `resource_id`: exactly one registered resource; no list in v0.1.0.
- `mode`: `auto` or `manual`.
- `suite`: a consumer label such as `install`, `migration`, or `regression`.
- `input`: a contained bundle root, an explicit `selected_files` list and an inventory digest. TASK-003 provides the internal selected-file sealer; TASK-033 local admission copies, verifies and binds the object before accepting the request. The submitted digest is the lowercase 64-character hex portion of the manifest's `tree_sha256` value.
- `environment`: the consumer profile reference and its expected digest, recorded as evidence for VM jobs; an explicit local environment reference for local jobs.
- `workload`: argv, bundle-relative working directory, non-secret environment, and required output declarations. Local execution resolves a bare `argv[0]` against the workload's `PATH` (default `/usr/bin:/bin`, overridable in the workload environment); a relative path containing `/` resolves against the declared working directory.
- `setup`: optional bounded argv for manual-mode preparation; ordinary install recipes may be the workload for auto mode.
- `manual`: required scenario document and completion schema only when mode is manual.
- `deadlines`: positive finite queue, preparation, run/manual, collection, and cleanup budgets. Native `submit` and `run` fill only active keys that are absent, using `GET /v1/operator/projection?view=config`, before strict decode and the canonical hash. Automatic mode fills queue, prepare, run, collect, and cleanup. Manual mode fills queue, prepare, manual, collect, and cleanup. An inactive key is not inserted. Explicit zero, null, a wrong type, a duplicate, or an unknown key is left for the strict decoder. A fully explicit spec does not call the projection and stays compatible with an older controller. A missing projection is an actionable error when a default is required; the CLI does not read the config file or a built-in default instead. A value above 366 days fails the existing job validator and is not clamped. The same request key with a different materialized spec conflicts and creates no Job. The server does not fill budgets. A direct API request is already fully resolved.
- `effects`: offline/live class and declared authorization/effect reference, containing no credential values.
- `provenance`: candidate identity, test identity, requested compatibility/profile owner, and development/release evidence class.

The provisional decoder rejects duplicate JSON keys at any depth, unknown fields, wrong types, unresolved placeholders, unsafe or case-colliding output paths, and empty required-output declarations. It requires an absolute clean bundle root, lower-case 64-digit SHA-256 digests and positive phase deadlines no longer than 366 days. Auto Jobs require a run deadline and omit `manual`; manual Jobs require a manual deadline, a contained scenario document and unique required scenario IDs, and omit the run deadline. These validation rules precede admission. TASK-033 seals local auto-Job input before admission and checks local resource readiness; later tasks own the remaining resource and execution paths.

No field lets a project replace the host UTM control program, VM identity, SSH identity, resource capacity, or cleanup policy. Those belong to operator-controlled resource configuration.

The request key is required for mutating submission. It is 1–128 ASCII characters, begins with an alphanumeric character, and contains only alphanumeric characters, `.`, `_` and `-`. Invalid keys are rejected before sealing or admission. A managed runner propagates a controller-verifiable parent execution context. A child holding capacity in the same installation cannot submit another Job or block on a non-terminal job's progress (`wait`, `events --follow`, `logs --follow`); non-blocking reads and observation of terminal jobs remain allowed. See [nested acquisition](managed-transitions.md#nested-acquisition). A project wrapper persists that key and the frozen input identity in ignored/private run metadata before its first submission, so an uncertain transport response can be reconciled without generating another key. Its scope is one Haepari installation, not the working directory; the R2 shared external namespace is deferred. The deduplication digest is the canonical digest of the submitted request: the validated typed structure, including alias names exactly as submitted, plus the sealed input digest. Resolved environment and resource-configuration identities are recorded with the admission but are not part of the deduplication digest, so an identical replay after a resource update or an alias move returns the original admission. No raw secret values participate. The same key and canonical submitted digest recover the original admission when the surviving selected inputs match the valid sealed inventory; missing selected paths remain permitted. A different digest, changed surviving input or invalid replay-comparison input conflicts without replacing the bound admission. A rejection before admission consumes no key. A new run after a known terminal failure requires a new key and a new explicit submission linked to the prior job.

Admission tombstones survive ordinary purging. A tombstone returns the known admission and an unavailable-result status without executing. There is no short timer after which an old request key silently becomes reusable.

The TASK-006 internal receipt uses `admission` for immutable sequence, request/submitted/input/object identities, original resource configuration revision, environment profile identity and UTC admission time. These are separate from the current resource revision and occupancy fields. A retained tombstone has `result_status: unavailable` with the known Job/admission identity, and omits verdict, capacity and lease fields. `submit` returns that known admission successfully; `run` emits it and exits 2 without waiting, and `wait` reports `RESULT_UNAVAILABLE` with exit 2. This is unavailable retained evidence, not a Job verdict or a rejected/new submission. `inspect` exposes the tombstone without a fabricated result. TASK-012 implements explicit bulk retention; missing accepted payloads without an explicit retention receipt are storage uncertainty.

## Event and wait semantics

Use HTTP over the private Unix socket for request/response operations and a documented streamed response for events. Every connection starts with a protocol handshake: the client sends its supported protocol version range, and the controller selects one and returns its capability set plus the stable installation ID used to check inherited advisory grants. If they share no version, the controller returns `PROTOCOL_UNSUPPORTED` before any mutation. There is no TCP listener by default or in the v0.1.0 public surface. An event cursor is monotonic and resumable. The server verifies cursor scope; if older events were explicitly purged, return a resynchronization response with the current snapshot, never a silent empty stream interpreted as success.

The provisional internal event page carries a Job-scoped `current_cursor` and a `next_cursor` for the returned page. A resynchronization response carries the Job snapshot and a retained Job-owned checkpoint cursor. Prefix retention preserves cursor ownership tombstones and the purge floor; a client resumes from the checkpoint after applying the snapshot. Cursor scope and the page are read from one SQLite snapshot. A cursor whose ownership was never recorded is rejected rather than attributed to a Job by guesswork.

The implementation may perform bounded internal liveness checks. TASK-008 uses blocking HTTP wait and versioned event/log follow over the private socket. Subscribe-before-read commit generations close the observer registration race; a fixed caller timeout is not renewed by unrelated notifications. User-facing skills and wrappers must use blocking wait/events rather than a status polling loop. The daemon remains the owner when a CLI process exits. A heartbeat indicates only connection liveness, not test progress or renewed execution authority.

### Implemented local observer wire format

The standalone `capabilities --json` response lists compiled feature identifiers in `capabilities`, separately from `protocol_versions`, `compiled_backends` and `qualified_backends`. The current local slice reports `managed-execution/v1`, `durable-observation/v1`, `advisory-lock/v1`, `managed-recovery/v1`, `artifact-delivery/v1` and `evidence-retention/v1`; this feature report does not claim live backend qualification.

Closed operation envelopes are bounded to 4 MiB, allowing result inventories and bounded observation pages above the 1 MiB input-document limit. Response payloads may contain literal angle brackets; illustrative input placeholders are not a response-validation rule. Known unavailable-result errors retain `RESULT_UNAVAILABLE` and exit 2.

The shipped client sends integer `X-Haepari-Protocol-Min`, `X-Haepari-Protocol-Max` and `X-Haepari-Protocol: managed-execution/v1` on every request, including hello. The controller requires the selected-protocol header on non-hello operations. The controller currently selects version 1, returns `protocol_version`, `protocol`, `capabilities` and `installation_id` from `GET /v1/hello`, and rejects malformed/missing or disjoint ranges with `PROTOCOL_UNSUPPORTED` before effects. Schema 6 persists the original installation identity across restarts and later relocation; an existing schema-5 root keeps its earlier derived ID at first binding. An unexplained missing identity row/table in schema 6 refuses opening.

`GET /v1/jobs` accepts `resource`, `state`, `cursor` and `limit` (1–100; default 50). Its closed page has `jobs`, `more` and optional `next_cursor`. Each entry includes `receipt`, a queued `queue_position`, and a retained terminal `result` when available. The opaque cursor binds the installation, exact filters, permanent admission sequence and initial upper bound. Queue position counts all earlier queued Jobs for that resource, independently of list filters. `GET /v1/resources` accepts `cursor`/`limit` with the same bounds and returns `resources`, `more` and optional `next_cursor` in resource ID order. Tombstones expose known admission/unavailable status without inventing a result.

The Job state filter accepts `queued`, `preparing`, `ready`, `running`, `awaiting_manual`, `cancelling`, `collecting`, `cleaning`, `settling`, `reconciling` and `finished`. Plain log pages report `LOG_MORE` on stderr with the next offset and identity when bytes remain; stdout contains only the exact bytes. Plain paged and followed log failures report the stable error code and bounded explanation on stderr, preserving the operation exit code.

`GET /v1/jobs/{id}/events` accepts `after`, `limit` (1–1000; default 100) and `follow`. Event pages include `snapshot`, `events`, `current_cursor`, `next_cursor`, `more`, and optional `resync`. The next cursor is the last returned event, not a high-water mark that skips a page. Explicit prefix retention returns a snapshot/checkpoint; unexplained lost payloads fail as storage uncertainty. `GET /v1/jobs/{id}/logs` accepts `after`, optional `identity` and `follow`. Log pages return `job_id`, file `identity`, `offset`, `next_offset`, observed `size`, base64 `data`, `more`, `snapshot`, and an optional explicit `gap`. Each data page carries at most 64 KiB. Resume a gap from its stated offset and new identity rather than silently appending unrelated bytes. Plain `LOG_GAP` diagnostics include both `--after` and `--identity`. A retained admission with `result_status: unavailable` returns `RESULT_UNAVAILABLE` for paged and followed events/logs; it does not emit a fabricated terminal stream.

Follow is one `application/x-ndjson` response containing `haepari.observer/v1` records scoped by `job_id`. `page`/`resync` carry the operation page and checkpoint; `heartbeat` carries only the last checkpoint; `end` follows a drained terminal snapshot; `error` carries a stable machine error. A connection closing without `end` is a transport uncertainty, not successful completion. Clients validate record bounds, scope and progression before applying a checkpoint. A managed nested caller cannot register a blocking nonterminal follow stream.

Local output is accepted only with its private `haepari.output-identity/v1` receipt naming the Job, claimed run, device and inode. Unbound replacements and missing output from an observed started run return storage uncertainty. An already attached reader may report a verified removal as a gap; it does not attribute an unbound replacement's bytes to the run. Older output files without this binding are not adopted automatically. The observer shares the live run's short spawn gate so the interval between a run claim and publication of its output binding does not look like lost evidence.

### Cancellation admission

`POST /v1/jobs/{id}/cancel` accepts `job_id`, positive `expected_revision` and permanent `mutation_key`. CLI `cancel` requires `--json` and uses `--request-key`; persist an explicit key plus the original expected revision for exact uncertain-reply replay. An omitted key generates a fresh identity that is returned only after a successful reply; save an explicit key before calling when exact uncertain-reply replay is required. Public cancellation keys are stored separately from internal runner mutation keys. The response separates the original `mutation`, current `receipt` and `cancellation` intent/status. Acknowledgement alone is not termination or cleanup evidence. Queued cancellation and reservation serialize in the ledger. Active intents remain sticky through collection/cleanup and unrelated revision conflicts cannot be retried as fresh effects. A known native outcome is imported before cancellation classification; late intents do not rewrite it. Terminal results remain immutable and later cancellation returns the existing result. Unknown termination remains reconciling/occupied rather than returning capacity. TASK-009 supplies the dedicated independent local runner. TASK-010 connects local cancellation and completed preparation failures to common bounded settlement; TASK-015 connects development VM execution and TASK-019 connects general manual completion.

## Manual completion

A manual result binds the job, exact installation/profile identity, expected current revision, observer label, each required scenario's `pass`, `fail`, or `unobserved` status, and bounded evidence references. It contains no authentication values. `unobserved` prevents PASS. Conflicting repeated completion fails; an exact retry recovers the original completion receipt.

The provisional `haepari.manual-result/v1` shape has `job_id`, `installation_id`, `profile_id`, `profile_digest`, `expected_revision`, `observer` and `scenarios[]`. Each scenario has an `id`, `status` and `evidence_references[]`; passing or failing observations require at least one reference. The exact required scenario set comes from the admitted Job. The decoder is implemented internally during TASK-002; TASK-019 connects CLI completion and its durable receipt. `manual complete` requires `--json`. The private HTTP operation is `POST /v1/jobs/{id}/manual/complete` with `result` (the closed manual record) and `expected_revision` matching the record. The scenario document must be in the sealed selected files. Optional setup and workload smoke use the original prepare budget and one native preparation identity; stopped smoke success only enables awaiting, never human PASS. Awaiting holds capacity until owned collection, cleanup and settlement. The original persisted manual deadline survives restart. Exact canonical completion replay returns its original receipt before testing current state, revision or deadline, including after settlement and retention; a changed record conflicts. First completion fences Job, installation, profile, revision, cancellation and deadline. Missing observations stay explicit and prevent PASS. Caller exit or wait expiry does not cancel; explicit cancellation and deadline retire completion authority. Unknown native/filesystem cessation remains occupied reconciliation. `RECOVERY_BLOCKED` carries a manual-specific reason when preparation is pending, the original deadline expired or authority retired; a known queued Job is not reported as missing. Invalid records name safe field/reason diagnostics without echoing record values.

Manual mode has no run deadline. Its admitted `manual_seconds` duration establishes the original UTC deadline when awaiting begins. Expiry retires completion with `workload_outcome=timed_out` and INCOMPLETE; it does not declare a human PASS, prove the human disconnected, or release capacity before settlement. For known long inspections the operator supplies an appropriate deadline before admission. Extensions, if implemented, require a current revision and explicit authorization; automatic indefinite extensions are out of scope.

## Consumer Make contract

`make test-vm SUITE=<consumer-suite>|all MODE=auto|manual` is implemented in the [runnable reference project](../../examples/project-test/README.md). It defaults to regression. Installation/migration recipes are optional consumer choices. The host wrapper saves sealed selected files, the exact specs and request keys before submission, then records the returned Job IDs before waiting. Reconnect with the same private `RUN_DIR`, resource, suite and mode; original installation identity and spec hashes fence replay. No replacement Job is created after an uncertain reply. Manual spec construction and controller execution are connected by TASK-019; setup/smoke readiness waits for revision-bound consumer observations before settlement.

`doctor --resource <id> --json` emits `haepari.doctor/v1`: installation/resource identity, current resource projection when registered, UTC observation time, `ready` and actionable `gaps[]` (`code`, `message`). Readiness requires no diagnostic gap. VM gaps distinguish host platform, Aqua session, private pin/mapping, readable/individual unexpired DHCP lease, running UTM identity and guest SSH/boot/platform/MAC checks; messages contain no raw private path or SSH output. For UTM it observes an existing Aqua session, running registered UUID, an unexpired individual DHCP lease, pinned SSH mapping/key, fresh challenge, boot identity and Darwin arm64 guest with the registered MAC present. It transfers no runner or project files and writes no guest state. A valid diagnostic envelope has `ok=true`; a gap makes the CLI exit 2. Missing controller connection emits `PREREQUISITE_UNAVAILABLE`, and the wrapper retains its actionable explanation. It does not warn about queue budgets, alter availability, reserve capacity or prove cleanup. Admission and dispatch still enforce current fences.

A failed post-probe resource re-read reports `resource_observation_unavailable`; it does not assert that the configuration changed. A confirmed revision/digest change reports `configuration_changed`.

TASK-023 M2b-2 F2 implements `haepari doctor --projection --section queue|retention`, with optional `--resource`, `--cursor`, and `--limit`, and required `--json`. Help lists `haepari.operator-diagnostic/v1` and keeps both doctor usage lines: `doctor --resource <id> --json` and `doctor --projection --section queue|retention [--resource <id>] [--cursor <cursor>] [--limit <1-20>] --json`. The command exits 0 for unknown, warning, and past. `clientFailure` stays as it is: `WAIT_TIMEOUT` is 5, `STORAGE_UNAVAILABLE` and `TRANSPORT_UNCERTAIN` are 6, and the other existing envelope codes are 2. When `--projection` is absent, `section`, `cursor`, and `limit` flags are rejected. `--limit` accepts only canonical integers 1 through 20, so an empty value, a leading zero, 21, and -1 exit 2 and are not sent. The client omits `limit` only when the caller passes 0, which selects the server default of 10. Any other client limit, including a negative value, is forwarded for the server's strict 400. The legacy resource-only route above is unchanged. The rejection gap is exit 2. This command does not invent exits 3 or 4. It has no eligible flag, no due flag, no deletion list, no purge, no GC, no schema 13, no `haepari.retention-projection/v1`, no new ErrorCode, and no constant checklist booleans.

The VM executes a distinct entrypoint, conventionally `make test-vm-guest` or `tests/vm/run.sh`. It requires the job/lease context that the guest runner provides before executing the guest entrypoint. The host wrapper must not be copied into an execution path that recursively submits another job. Ordinary `make test` remains unchanged unless a separately adopted repository policy deliberately adds an external gate.

`SUITE=all` is a serial host wrapper over only the consumer-declared suites as distinct Jobs, all bound to the same candidate/test bundle. It retains every job ID and reports skipped suites after a failure. Do not claim aggregate PASS unless every required suite and manual check completed.

A wait-expired wrapper reports `PENDING`, while a non-verdict transport/storage observation failure reports `UNKNOWN` and preserves the CLI error exit. Neither is a terminal Job verdict or cancellation.

The saved declared-suite list and unique Job/key/spec bindings must remain complete
on reconnect. Empty, truncated or inconsistent records fail before dispatch or
aggregate PASS; retain the original specs and keys for inspection rather than
silently rebuilding a request.

## Machine outcomes and glossary

The proposed `haepari.result/v1` fields are `job_id`, `resource_id`, `resource_revision`, `lease_generation`, `job_state`, `resource_availability`, `workload_outcome`, `evidence_completeness`, `cleanup_outcome`, `final_verdict`, `timings`, artifact inventory and observation provenance. `timings` holds UTC timestamps for admission, reservation and the start and end of each phase. It also holds adapter step durations reported by the adapter: for UTM these are VM start (when needed), SSH ready, transfer, collection and cleanup. Queue wait and VM cycle phases are derived from it. See the [local result example](../examples/result-local.template.json). TASK-010 populates admission/reservation/entered-phase timestamps for completed local paths and admission timing for queued terminal paths. It records no start/end for an unentered run. VM results project observed `vm_start` (only when this controller issues and confirms that start), `ssh_ready` and `transfer` preparation durations, followed by `collect` and `cleanup` phase elapsed durations. Preparation observations are persisted with their completed lease-bound phase receipt; historical or interrupted preparation can omit unavailable measurements. Collection and cleanup elapsed time includes any reconciliation interval and does not imply successful effects. Local results retain an empty adapter-step list.

The provisional result type has separate optional `native_exit_code` and `native_signal` fields so an observed workload command exit is retained without becoming the CLI exit. For manual completion, preparation native facts remain separate in the original preparation record; human PASS or FAIL does not invent a native exit or copy the preparation exit into the human result. A complete PASS or FAIL requires the artifacts declared by the admitted Job; unknown outcome values and contradictory terminal verdicts are rejected. A queued or reserved no-effect result records `cleanup_outcome=not_needed` without inventing a workload output. The internal ledger binds a no-effect machine observation's reference, mechanism and digest to the exact Job, resource revision, slot and lease before classification, and refuses settlement while a VM power transition is pending or uncertain. TASK-033 and TASK-016 supply and qualify the actual local and VM observations; this provisional record alone is not runtime qualification.

A **request key** deduplicates admission; a **job ID** identifies the accepted managed Job; a **lease generation** fences one resource-slot ownership; a **run ID** binds the single supervised workload; a **resource revision** fences configuration/recovery; a **profile** is a consumer-owned frozen environment selection that Haepari records but does not apply to the VM. A **wait timeout** ends only observation. **INCOMPLETE** is a known terminal verdict with missing proof, while **FAIL** is a known workload/assertion failure. A rejected input has no admission. A transport uncertainty requires inspection or resubmission with the same key, never a new speculative job.

Machine error codes and their exits are listed under [JSON envelopes and exit codes](#json-envelopes-and-exit-codes). Terminal result envelopes carry `PASS`, `FAIL`, `CANCELLED` or `INCOMPLETE` separately from `ok` for the command. The [authoritative decision table](managed-transitions.md#authoritative-final-verdict-decision-table) controls all combinations: a known workload failure with complete evidence and verified cleanup is FAIL; missing required evidence, unverified cleanup or required unobserved manual work makes the final verdict INCOMPLETE while preserving the failure fact. A reserved proven no-effect Job may finish with `cleanup_outcome=not_needed` and one capacity return; queued cancellation uses the same cleanup value without a reservation or capacity return. A VM-local `vm_unavailable` pause commits before its reserved Job settles and does not pause other resources. A queued Job blocked by host VM policy or capacity exposes its current actionable blocking reason through inspection and events without changing its queue deadline. Terminal results are immutable; later recovery evidence has separate receipts.

## Recovery mutation contract

`job recover --plan` and `resource recover --plan` return exact installation, job, resource, config revision, slot/generation, run/boot/nonce, last durable intent and receipts, current observations, unknowns, proposed effects and evidence loss. Supported actions include a short-lived token bound to that snapshot; blocked or unsupported actions omit it. The operator has local control authority over the owned resource and explicitly invokes apply; the token alone is no substitute for authorization. Apply checks the entire tuple and expected revisions transactionally before effects and records mutation intent and receipt. Evidence has source, observer, observation time, mechanism and digest/reference. Machine-observed termination can permit normal collection and cleanup. Operator-attested termination or non-execution is labeled attested, can only resolve the stated resource/job under the declared policy, never upgrades workload outcome to PASS, and remains visible in result provenance. An unverified timeout, lost CLI, stale PID, or controller restart is insufficient. Failed cleanup quarantines; proven cleanup returns readiness. Replayed apply returns the original receipt; stale or changed plans reject without effects.

## Implemented artifact, retention and help surface (TASK-012)

`haepari help --json` reads no controller and emits `haepari.help/v1` inside the ordinary envelope. It lists implemented commands and their flags, supported schemas, outcome/state enums, error/verdict exits, canonicalization, cursor behavior and current default bounds. `capabilities` and Unix hello share the same six implemented protocol capabilities; compiled command support remains distinct from backend qualification. Existing managed commands serve implemented local and automatic development VM Jobs; selected-resource doctor is implemented. General local/development VM manual completion is implemented by TASK-019; VM resource removal and release commands remain planned.

`haepari export <job-id> --to <absolute-directory> [--json]` writes verified retained evidence to a fresh explicit destination. Its success receipt identifies Job, destination and file count. `haepari purge <job-id> --expected-revision <n> --json` returns `haepari.purge-receipt/v1` with original admission and `complete`; repeat the saved revision after an interrupted deletion. Inspect the current Job receipt before the first purge. No implicit overwrite, export location or expiry is selected. See [delivery and retention](artifact-and-profile.md#implemented-delivery-and-retention-task-012).

Unix routes `GET /v1/jobs/<id>/artifacts` and `POST /v1/jobs/<id>/purge` expose the same contract. Manifest GET has no query parameters. Page GET requires `path`, `after`, `sha256`, `size` and `page_token`, each once; unknown, malformed, duplicated or out-of-bound parameters reject. The page size is at most 64 KiB and offsets are exact bytes. JSON data is base64, without interpreting file contents.

`resource recover <id> --plan --action recollect|dispose --json` plans protected-evidence recovery. Apply uses the returned token and saved `--request-key`, with no operator evidence file. It records a typed supplementary evidence receipt; an identical completed request replays after restart or token expiry. Disposal plans identify the precise lost references. Failed collection stays protected; successful collection/disposal does not lift quarantine by itself. A subsequent default resource-health plan/apply is separate and cannot rewrite the original result. Unsupported production VM plans are inspection-only with no token.

After purge, `submit` returns the same unavailable admission, `run` emits that admission and exits 2, and `wait`, `events`, `logs` and artifact reads report `RESULT_UNAVAILABLE`. Saved cancellation mutation replay remains exact. Event cursor ownership is checked before result availability: a cursor recorded for another Job is `INVALID_REQUEST`, even after purge. Purged payloads retain their permanent cursor owner and floor.

F1's decision, initial delivery change inventory and field/compatibility decisions are recorded in the [managed core freeze record](../records/TASK-012-managed-core-freeze.md). It takes effect when TASK-012 is Accepted in the canonical roadmap; F2 VM fields and F3 manual/consumer formats remain separate gates.

`resource recover <id> --plan --action attest-power-stopped --json` plans cessation of one unresolved power transition involving that resource. Apply requires the saved token/key and a scoped operator evidence file; it never issues power or synthesizes command return. The plan identifies both resources and the original generation/claim. No unresolved transition is a power-specific refusal; multiple matches violate the supported ledger invariant and remain protected for investigation. Guest cessation uses the separate `attest-guest-stopped` action. See the EPIC-009 recovery runbook for each evidence chain.

## Versioned absence-aware admissions (TASK-036)

`haepari.job/v2` uses the same closed fields and admission canonicalization as v1, selecting the approved absence-aware settlement policy in [managed transitions](managed-transitions.md#epic-009-approved-recovery-delta-task-036). Every newly settled result for that admission uses `haepari.result/v2`; persisted v1 keys and results keep their original identities. The Unix transport/envelope protocol remains v1. Machine help advertises both supported Job/result versions and v2 recovery plans. Bounded `haepari.diagnostic/v1` event payloads supplement public Job events with classification codes; paths, secrets, argv, environment and raw SSH/provider output are excluded.

Failed recovery/v2 observations can append bounded, deduplicated diagnostic events to an available retained finished Job. Such events are supplementary: they change no Job revision, immutable result, capacity, resource availability or recovery authority. Purged admissions cannot receive new diagnostic history. Ordinary diagnostic recording retains its terminal guard, and successful exchanges emit no failure event.
