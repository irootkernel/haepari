# Resource, UTM, and runner contract

## Resource definition

`haepari.resource/v1` is operator-owned configuration. It names `id`, `kind` (`local`, `utm-macos` or `lock`), `execution_mode` (`managed`, for `local` and `utm-macos` only), positive capacity and configuration revision. A `lock` resource has no adapter or execution; the [lock contract](locks.md) defines it, and it counts toward no managed or global capacity. `local` and `utm-macos` require managed execution. Definitions include owned paths, pinned adapter identities and lifecycle budgets. A `utm-macos` definition names one persistent, operator-owned UTM VM ([ADR-0018](../architecture-decision-records/0018-persistent-vm-no-reset.md)): its UTM VM UUID, the MAC address used for address discovery, the pinned SSH host key and SSH mapping, the guest job root that Haepari owns, and `vm.allow_automatic_stop` (boolean, default `false`). This operator authorization permits capacity-driven forced stops only while the resource is otherwise eligible; absence of a Haepari Job does not establish that guest services or operator work are safe to interrupt. Two resources cannot name the same VM UUID or MAC address. A job's profile digest is consumer evidence that Haepari records; it is not matched against the VM, which keeps whatever earlier jobs left. A local job names an explicit local environment reference instead. Public external resources are deferred; reject them as unsupported in v0.1.0.

A submitted job cannot overwrite this definition. Local resources may use a trusted operator-defined prepare/cleanup command; job inputs supply only workload bytes and permitted parameters. A resource advertised as isolated must actually use an isolating backend. The generic local adapter makes no sandbox claim. For a local command resource, reusable means the owned process group has settled and its declared cleanup/health checks passed; it does not mean arbitrary host filesystem changes were rolled back. Shared-state resources such as a test DB require operator-provided reset and verification hooks.

Registering or updating a `utm-macos` resource is revision-fenced. It checks that UTM lists a VM with that UUID, that no other resource names the same UUID or MAC address, and that the SSH host key pin is present. Registration never creates, clones, boots or deletes a VM. The current host adapter resolves `guest.known_hosts_reference` as `sha256:<lowercase-file-digest>:<absolute-path>`. The regular, non-symlink, non-group/world-writable OpenSSH file contains exactly one `ssh-ed25519` public key for alias `haepari-vm-<lowercase-VM-UUID>` (comments and blank lines are allowed). It accepts no address aliases, wildcards, hashed hosts or marker directives. Registration and later resolution verify the same file digest; changing a pin requires an explicit configuration revision. No host-key discovery or trust-on-first-use occurs. TASK-014 resolves `guest.connection_reference` as `sha256:<lowercase-file-digest>:<absolute-mapping-path>`, as described below; VM fields remain provisional until F2. Configuration changes need an idle resource with no pending or uncertain power transition. Removing a resource never deletes its VM.



## Adapter phases

Every Job-phase managed adapter call carries the job ID, resource ID, expected resource/configuration revision, lease generation, nonce, input/profile digests, and phase deadline. Responses identify the same tuple. Capacity-driven victim stops use the separate internal power-transition intent, which binds the victim and target identities/revisions and target Job/lease generation; an idle victim has no Job lease to borrow.

| Phase | Allowed effects | Required evidence |
| --- | --- | --- |
| Inspect | Read registration/capabilities only | Exact identity and readiness/gaps |
| Prepare | Start the VM if it is stopped, connect, stage input into a fresh job directory | VM identity (UUID, MAC-to-address lease, SSH host key), guest/run identity, staged digests |
| Execute | Start or reattach one exact runner | Durable run claim, start identity, observation endpoint |
| Collect | Read declared outputs into the owned host job root | Artifact inventory, sizes/digests, completeness |
| Cleanup | Prove owned workload/collector termination; remove Haepari-owned files only when no required uncollected evidence is protected | Termination proof, removed or protected-path inventory and reason |
| Verify | Check the VM identity, that no Haepari runner remains and that no protected owned path blocks reuse | Verified reusable state or quarantine reason |

If preparation produced no owned Job effect requiring cleanup and left no protected evidence obligation, Job cleanup can be `not_needed`; a VM start is a separate power prerequisite that must still be reconciled. An effectful path whose cleanup succeeds records `verified`. After any possible Job effect, failure or timeout invokes collection and cleanup within their own limits. No adapter returns reusable=true from a process exit alone.

## UTM control

UTM documents a CLI wrapper around AppleScript. Its examples for guest command and file access assume a QEMU Guest Agent, which a macOS guest on the Apple backend does not have. The Haepari protocol does not invent unavailable `utmctl` flags. See [S1 through S3](../sources.md).

TASK-034 probed the installed UTM version, Apple backend, host OS and `utmctl` behaviour in a logged-in, unlocked session ([probe record](../records/TASK-034-utm-probe.md)). TASK-016 qualifies them, together with the guest OS and the behaviour when the screen is locked or the user is logged out. Missing ability to complete a safe job cycle blocks the backend. Do not silently switch to QEMU, a beta build, or a different VM manager.

The v0.1.0 strategy is one persistent VM per resource, with no reset between jobs ([ADR-0018](../architecture-decision-records/0018-persistent-vm-no-reset.md)). The adapter must:

1. Control the VM only through `utmctl` `status`, `start` and `stop`, addressed by the registered UUID. It never runs `clone` or `delete`. It uses neither AppleScript, which raised an Automation prompt in the probe, nor UTM's data container, which was unreadable.
2. Treat a `utmctl` call as failed when it exits non-zero or prints `Error from event` on stderr. On the Apple backend, `ip-address` fails this way with exit 0.
3. Use the VM when `status` is `started`, and start it when it is `stopped`, within the host guest limit. Any other status, such as `paused` or `starting`, makes the VM unavailable (see below). Find its address in the host DHCP lease table by the registered MAC address under the lease validity rule below, and connect over SSH with the pinned host key.
4. Transfer only the sealed input bundle and the job's guest runner into a fresh job directory under the guest job root. Validate it before project installation begins.
5. After execution, establish owned workload termination, collect evidence with a bounded collector, establish collector termination, and remove the job directory only when doing so will not destroy required uncollected evidence. If evidence must remain, durably record its owned paths and gaps, quarantine the VM, and use the [recovery contract](managed-transitions.md#evidence-preserving-settlement). Whatever the workload changed elsewhere in the guest persists; consumer recipes own their starting state and cleanup.
6. Do not shut the VM down after a job. Force-stop it with `utmctl stop` only to make room under the host guest limit (see below) or during recovery. `utmctl stop --request` is not used; it did not stop the probed guest within 240 s.

A name match, empty `utmctl` output, or a successful command alone is not identity evidence. Haepari never edits a VM package.

Reset strategies, such as a whole-VM copy, UTM snapshots or a disposable start, are outside v0.1.0. A beta UTM release documents snapshots and a disposable start mode for Apple Virtualization guests on macOS 27 ([S9](../sources.md)); adopting one later needs its own decision and qualification.

## SSH and guest supervision

Use the configured system SSH/SFTP executable through argv, with pinned known-hosts material, BatchMode, no agent forwarding, no ambient remote command configuration, and bounded connection timeouts. Paths and values that cross the remote shell boundary are encoded through a fixed runner request file; a project command is not concatenated into `ssh ... "..."`.

The guest identity check combines the pinned SSH host key, the registered VM UUID and MAC-to-address lease, observed OS/architecture, boot identity, and a fresh nonce. Credentials are handled as secret references or preprovisioned guest state with explicit approval, never as input-bundle files.

**Implemented TASK-014 boundary.** The mapping file is canonical compact JSON with exactly `schema` (`haepari.ssh-mapping/v1`), `user`, `port` (1–65535) and `identity_file` (absolute path). It is a private regular file owned by the host user, bound to the raw file digest. The referenced private key is a private, single-link regular file owned by that user; only OpenSSH reads it. No key bytes enter the transfer or input bundle. The operator provisions Remote Login, authorization and the host-key pin separately. The adapter uses an explicit system SSH executable, `-F /dev/null`, a fresh snapshot of the verified dedicated pin, strict checking, the VM alias, ed25519 host keys, BatchMode, one explicit identity, no authentication agent, no password/interactive fallback, no agent or port forwarding, and one bounded connection attempt. An ordinary SSH alias is diagnostic setup context, not a resource identity or product connection mapping.

`internal/utm.SSH.Call` checks the current started VM and individual lease through TASK-013 before each operation. A fresh challenge is returned by the digest-pinned guest executable along with its actual interface MAC, Darwin arm64 platform and boot UUID. The VM UUID is the registered host-key alias binding, not a claim that the guest can independently read UTM metadata. Reattachment requires the original boot and request identity. A mismatched pin, challenge, MAC, UUID mapping, platform or boot fails before project installation. Lease expiry is rechecked before issuance and after response; there is no address fallback.

The remote command is one constant bootstrap. A generated archive contains only three fixed regular-file names: the pinned executable, structured request and executable digest. Project paths, argv, environment and inventory are JSON data, never interpolated into shell text. The bootstrap uses a new private temporary directory under `/private/tmp`, verifies the binary SHA-256, invokes `runner guest --stdio`, and removes only its three bootstrap files on normal exit. Transport loss can leave bootstrap residue for diagnosis; it grants no permission to remove a guest Job. Each new Job receives its own runner copy and canonical sealed inventory in a fresh, private owned directory; inventory, per-file hashes and modes are validated before project execution. Payload publication uses directory descriptors and no-follow exclusive writes. The current protocol accepts at most 96 MiB of request JSON and a 64 MiB runner; exceeding these bounded internal transport limits refuses rather than truncates input. Larger transfers are not claimed at this checkpoint.

The internal `haepari.guest-request/v1` / `haepari.guest-reply/v1` protocol offers identity, prepare, start, inspect, watch, cancel and 64 KiB offset output reads. TASK-015 adds state, root, file, retire, cleanup and health observations/effects with a guest-native filesystem-worker receipt and exact root incarnation. Each operation binds the original input object/tree and profile digests, run/lease/configuration identity and phase deadline. The reply includes the canonical protocol-request digest, and closed-shape decoding rejects missing, null, duplicate or case-aliased required fields. Expired phases cannot authorize a new launch. Prepare returns the exact native request, including the guest output device/inode. Completed preparation is observable again without copying; partial preparation remains protected for exact TASK-015 recovery. A synced immutable `launch.json` claim precedes detached supervisor creation. Repeated start observes that claim and original receipts; a claim without runner intent is `launching`, retains ambiguity and is never spawned again. The supervisor starts in its own session with closed transport descriptors and the per-Job pinned executable. Original runner receipts use the same file-sync, exclusive rename and directory-sync protocol as local execution. Inspect and bounded watch return original receipts; output reads check the original native file identity. Cancellation publishes the exact immutable cancellation and waits for proven native termination; killing an SSH observer establishes no workload termination. Host receipt validation compares guest identities without treating guest PIDs as host PIDs.

A failed or invalid response after an operation is issued is `ErrGuestUncertain`, not a proven no-effect prerequisite failure. No issued workload or unresolved filesystem operation retries automatically. The caller preserves the original request, run and lease and reconciles through TASK-015. Automatic development VM Jobs, explicit readiness-verified resume and Job/resource recovery are implemented; VM resource removal is unavailable. TASK-016 owns real SSH/UTM qualification and F2.


The transient runner accepts an authenticated, contained run request and provides `start`, `inspect`, `watch`, and `cancel` operations. It is launched using a qualified detach/supervision method that survives transport loss. It writes a durable request/spawn intent, actual start receipt when known, append-only output, and exit receipt under an owned guest job path, following the [receipt protocol](#runner-receipts). The digest-pinned runner artifact travels with each job's sealed bundle. Repeated start for the same run is idempotent; a conflicting request is rejected. A recorded ambiguous spawning state cannot be restarted automatically.

`watch` blocks on the same run. On transport loss the host may reconnect and observe; it must not invoke the original test command again. A guest reboot changes boot identity and prevents blind PID reuse. Cancellation waits for owned workload termination and still requires the job's cleanup. Stopping an SSH process does not terminate the semantic job.

### Implemented VM collection and recovery (TASK-015)

The controller binds one future run, original native request/boot, sealed input and frozen executable before guest preparation. It checks a 48 MiB aggregate input payload and the 96 MiB encoded guest request limit before issuing preparation, with refusal rather than truncation. Host and guest Job directories are separate; no writable host mount or host-side project recipe is used. The current global active limit remains one. `daemon run --host-macos-guest-limit 1|2` selects the host VM limit, default one; the full configuration loader remains TASK-023.

Each guest Job has an owned, single-link control receipt outside its directory (`haepari.guest-control/v1` for v1 exchanges; v2 uses `haepari.guest-control/v2` with the workspace binding described below), serialized with a native advisory lock. It records exact boot/request/root identity and the filesystem worker's native birth identity. State observes completion or positively established worker death; SSH observer loss establishes neither. An unobserved start can settle as no-start only after a durable retirement intent and guest retirement barrier refuse any delayed prepare/start. An ambiguous native launch claim is not a no-start observation. Cleanup of partial or prepared work requires retirement; completed workload cleanup requires native termination proof.

The durable prepare intent claims its private Job name before directory creation, and root binding precedes all payload writes. If the preparer stops between those steps, read-only state may observe the current root only after exact original request/boot identity, proven worker stop, private directory ownership, emptiness and unchanged directory incarnation are checked under the same lock. A nonempty unbound root is rejected without deletion. Retirement revalidates and syncs the observed root binding before it authorizes cleanup; preparation and workload execution are not retried.

Ordinary workload cleanup and retired partial-preparation cleanup pass the original bound root device/inode to the deletion operation. Deletion checks both the current directory entry and the opened directory against that identity before traversing any children. A replacement between the earlier validation and deletion is a conflict: its files are preserved, cleanup remains unresolved and health cannot declare the resource reusable.

Required files are single-link regular files reached through no-follow contained paths. Collection pins size, device/inode, modification time and whole-file SHA-256, reads at most 64 KiB per page, and verifies the complete host stream before exclusive durable publication. The default required-output bounds remain 1000 files and 1 GiB; native combined output has its separate 256 MiB bound. Existing exact host artifacts can be adopted after interruption only after file sync and sync of every publication parent through the exact host Job root, under the saved collection deadline. Sync failure or expiry prevents completed collection and guest deletion. Changed or incomplete files do not become published complete evidence. Guest deletion also requires revalidation of the published host artifacts/logs. Attested health that reconciles an absent root with its matching outside cleanup intent must complete the guest parent directory sync under its health deadline before returning reusable; this also covers interruption immediately after root unlink.

Failed required collection preserves the exact guest Job root with gaps and retention reasons. In VM results, protected path `workspace` with `job:<id>` is the logical recovery alias for the entire owned guest Job directory, including native logs and receipts; it is not a host path. Proven workload and collector termination permit INCOMPLETE settlement with quarantine and one capacity return. Unknown workload or collector lifetime keeps occupancy in reconciliation. Cleanup/health failure blocks reuse. Revision-bound recollection stores a separate supplementary inventory and may recover missing host log bytes; explicit disposal records evidence loss before deletion. A separate fresh health plan enables reuse, without rewriting the original result or evidence gaps. Minimal control metadata outside the removed Job directory is retained for original-identity recovery and delayed-request refusal.

Native VM recollection and disposal plans check the original guest termination receipt as well as filesystem-worker completion and root incarnation. A stopped filesystem worker, presently absent native owners or controller-side operator attestation cannot replace an immutable `termination_proven=false` exit for guest file access or cleanup. Such plans expose the missing native termination proof and issue no executable token. Apply and resumed effects revalidate these prerequisites; authorized evidence loss does not itself authorize deletion without termination proof. Disposal retains the existing retirement exception for prepared or partial work with no native spawn intent; that exception does not authorize collecting outputs without native proof. Separate health still requires owned directory absence and the guest's native stopped or retired no-start condition.

The returned `VZErrorDomain` code 6 start rejection is recognized narrowly; a fresh stopped observation and durable returned/no-effect proof are required before resolving its power intent. It follows the host-wide `host_vm_limit` pause path and INCOMPLETE/not-needed settlement. Generic command failure, interruption or a changed target retains power uncertainty. A VM-local pre-claim identity/lease failure uses the atomic `vm_unavailable` pause and no-effect settlement path; stale proofs cannot pause a new registration or clear existing quarantine.

## Runner receipts

Local and guest runners keep receipts as files in an owned run directory: `request.json`, `intent.json` (spawn intent), `start.json`, `outcome.json`, `exit.json` and append-only output. The implemented local runner also accepts an immutable `cancel.json` intent; cancellation acknowledgement alone proves no termination.

TASK-009 implements the Darwin local boundary. The controller launches the same executable as `runner start --request <absolute-owned-path>/request.json` in a separate session. The runner holds an exclusive kernel `run.lock` until exit. Concurrent starts return the existing receipts; `prepared` can briefly describe a held claim before intent publication and is never proof that no supervisor exists. Every request binds Job/resource/configuration, zero-based slot, lease generation, run ID, nonce, boot-session UUID, explicit argv/environment, contained working directory, UTC deadline, bounded run/termination durations and output device/inode. Every subsequent receipt binds that exact identity and the SHA-256 of canonical request JSON. Internal receipt schemas are `haepari.runner-{request,intent,start,outcome,exit,cancel}/v1`; these remain provisional until F1.

Receipt directories and files must belong to the current user, be private and have no symlink components; files must be regular with one link. Readers bound size to 2 MiB and reject duplicate, unknown and case-aliased keys. Intent/start identities include boot UUID, PID, birth seconds/microseconds, PGID, SID and UID. An exit must repeat the recorded workload outcome exactly. Missing or conflicting receipts retain uncertainty rather than authorize a new execution.

**How each receipt is written:**

1. Write to a temporary file in the same directory.
2. Sync the file.
3. Rename it into place.
4. Sync the directory.

**Order of events:**

1. The controller commits the exclusive run claim and exact request to SQLite before publishing the request or launching the supervisor.
2. The runner writes `intent.json` before spawning.
3. It starts a gated trampoline in its own session and writes `start.json` once that process identity is observed. Only then can the gate permit explicit workload `exec`; supervisor death before gate release causes EOF and prevents workload effects. The start receipt identifies the native execution container. `outcome.started=false` reports an explicit failure to enter workload exec; a released gate without that failure remains potentially effectful, including interruption around exec. An inherited close-on-exec status pipe distinguishes failed exec from an actual workload exit 126.
4. It writes `outcome.json` after native completion, preserving exit code or signal independently of cleanup. A proven no-start result is `inconclusive` or `cancelled`, without an exit code or signal, even if the deadline expired before the gate opened; `timed_out` requires an entered workload.
5. It writes `exit.json` after bounded descendant termination and output synchronization, with an explicit termination proof or unresolved reason. Controller collection, workspace cleanup and resource reuse remain separate.

TASK-012 stdout/stderr use a supervisor-owned bounded pipe drainer into the bound `output.log`. The drainer continues beyond the log limit or write failure, records the actual prefix and explicit gap, and must finish before proven exit; the controller owns no copy pipe. The supervisor scans same-user native ancestry/session observations, retains discovered birth identities across reparenting or `setsid`, and rechecks the complete current identity before each TERM/KILL. TERM grace and escalation share one termination budget. Group absence alone is insufficient. Darwin descendant discovery remains best effort under the [TASK-004 host decision](../records/TASK-004-macos-supervision.md); an escaped process that was never observable cannot be ruled out by this mechanism, and the local backend is not a sandbox. An incomplete scan, identity conflict, supervisor loss or expired termination budget keeps occupancy and quarantines the resource.

Cancellation writers serialize within the request's termination budget and accept an already durable, exact-bound cancellation from another writer. A conflicting cancellation or exhausted observation budget retains uncertainty. Runner receipts are immutable. TASK-010 records controller collection and cleanup intents and observations as immutable SQLite events, as specified by the [managed phase contract](managed-transitions.md#implemented-local-phase-receipts-task-010). TASK-012 publishes controller `input.json` and output-identity binding immutably through verified private directory descriptors, syncs before publication and directory-syncs completion. Conflicting replay or a replaced/link root refuses without overwriting evidence.

When native supervision first encounters uncertain workload start observation, process census, cancellation observation, signaling or group probing, it writes a separate private immutable `native-diagnostic.json` artifact using the same publication discipline. The artifact binds the original run/request digest and boot, run phase, triggering operation and UTC observation time. It retains a fixed error category and, when known, native observation operation, PID and errno; arbitrary error text, argv, environment and credentials are excluded. Later stop failures do not replace the first diagnostic. A diagnostic publication failure remains an error while supervision still attempts its bounded stop and records uncertainty. This optional artifact is diagnostic context only: it changes no request/exit/guest wire schema, is never consumed as termination proof, and does not rewrite historical receipts. Existing frozen guest runners do not acquire this artifact retroactively.

**How the controller uses them.** The controller imports receipts into SQLite. A missing later receipt is uncertainty, never success. After a restart, `intent.json` without `start.json` marks the ambiguous spawn window: resolve it through process evidence or leave it uncertain, and never spawn again.

Schema 8 stores exact request/receipt bytes and digests in `managed_runner_receipts`, fences imports against the current run identity, and rejects conflicting replay or a missing predecessor. Import events do not change Job revisions or public cancellation replay identity. Migration creates no receipts for earlier runs and refuses a missing current-schema receipt table. TASK-011 reads these receipts during startup and reattaches only a freshly observed matching supervisor incarnation. A consistent stopped receipt resumes collection/cleanup/settlement without another workload start. Missing or conflicting observations remain occupied and quarantined; explicit recovery uses the revision-bound plan described in the CLI contract. TASK-010 owns the common phase/settlement matrix.

## Recovery and fencing

Before forced recovery, produce a plan naming the exact VM, resource revision, current lease/run, evidence that may be lost, and proposed stop effects. The confirmation token binds those observations. A changed revision or new lease invalidates the token.

Recovery either proves the original execution state and finishes normal collection and cleanup, or records INCOMPLETE with protected required evidence. If owned workload or collector termination is unproven, the Job retains occupancy in reconciliation. If termination is proven but required guest evidence is retained, the Job may settle INCOMPLETE and return occupancy while the resource stays quarantined. Resource recovery re-collects or explicitly disposes of that evidence, removes owned files and verifies health before reuse. Recovery never fabricates a workload PASS or rewrites a terminal verdict. Other resources can continue.

The managed resource lease authorizes Job effects. The internal power-transition intent authorizes a capacity-driven stop of an idle victim; it cannot be inferred from the target Job lease alone. A recovery token prevents stale cooperating components from changing newer state; it is not an OS security barrier against same-user code.

## VM timing observations

The run phase fixes an absolute execution deadline before issuing guest start. The guest durably binds that deadline in its exclusive launch claim before spawning, capped by the immutable prepared request's deadline. The supervisor and final exec gate consume that saved deadline; delayed start, observation loss and controller restart cannot extend it. Start replay with a different effective deadline refuses without another execution. Historical claims without this optional private field remain ambiguous and never authorize a replacement supervisor. Native request and exit wire shapes remain unchanged; frozen historical guest executables retain their original behavior.

Completed VM preparation may carry optional adapter-step durations in its existing phase receipt: `vm_start` covers the current controller's fenced native start through confirmation, `ssh_ready` covers authenticated identity resolution, and `transfer` covers pinned guest preparation including renewed identity checks. A restart consumes the recorded measurements; it does not repeat an effect to reconstruct a missing duration. VM result collection and cleanup durations project their durable phase start/end timestamps, including reconciliation time and unsuccessful or retained-evidence outcomes. These measurements change no deadlines, lease or verdict semantics. Historical phase receipts omit the optional field, local phases cannot supply it, and neither the phase nor result schema identifier changes. Real qualification of the installed timing candidate remains TASK-016.

## Host session and VM identity

VM UUID identity comparisons are case-insensitive, and internal inventory keys are lowercase. Each `status`, `start` or `stop` first resolves the UUID from the current `utmctl list` and passes the exact observed spelling as a literal argument. Native UTM lookup can be case-sensitive. Membership lookup and the subsequent command share one ten-second deadline; missing membership or duplicate entries differing only in case refuse the operation before that subsequent command. Power commands remain single-effect calls without retry under the durable claim described below.

Guest identity and readiness requests use lowercase UUID and colon-separated MAC identity values, including after explicit resume. Registration retains the operator's accepted spelling, and native UTM commands retain the observed inventory spelling.

Host UTM control runs `utmctl` from the development or release LaunchAgent in the logged-in Aqua session. The TASK-034 probe observed an ad-hoc-signed LaunchAgent without an Automation prompt; it did not require a signing certificate. The current `make build` CLI embeds `io.rootkernel.haepari`, its name and Automation usage description in `__TEXT,__info_plist` before ad-hoc signing. This keeps the signature self-contained when the same executable is transferred alone as the guest runner; a new installed candidate still requires TASK-016 permission and backend observations. The UTM command-line tool states that it does not work from SSH sessions or before login ([S10](../sources.md)). SSH execution inside the guest is a separate transport and has its own login/key prerequisites. The controller's local queue and local-command backend do not require an Aqua session merely because UTM control may. **Recording.** Record the observed UTM, macOS, backend, user-session and permission tuple during TASK-034 and TASK-016. A version list in a report is not qualification evidence.

**Loss of session or capacity.** Session or host-capacity loss blocks new VM dispatch temporarily. A VM whose job processes or cleanup Haepari cannot confirm is quarantined.

**Host macOS guest limit.**

- Apple's macOS license allows at most two additional macOS instances in virtual machines per Mac, and the Virtualization framework reports a limit error when one is exceeded ([S11](../sources.md)). The operator's own VMs count too.
- The controller setting `host_macos_guest_limit` (default 1, schema maximum 2) bounds registered VMs that are running, starting, or in an uncertain power transition. When a Job needs a stopped VM at the limit, Haepari may force-stop the longest-idle **registered** VM with `vm.allow_automatic_stop=true`, no Job occupancy, availability `available`, and no pending/uncertain power transition. Paused resources are protected for maintenance even with no Job. Quarantined, recovering, occupied and transitioning resources are also ineligible. No unregistered VM is selected or stopped.
- **Longest-idle ordering.** Persist a UTC `idle_since` when managed occupancy changes from one to zero, or at registration of a new resource with zero occupancy. Compare this value ascending, then resource ID ascending. Restart, configuration updates, pause/resume and queued cancellation/expiry do not reset it. A legacy resource whose historical idle time cannot be established has an unknown value and cannot be selected automatically until a trustworthy one-to-zero transition supplies it.
- One short SQLite transaction reserves the requesting Job and its target-start claim, records the selected victim's power-transition intent, and binds the target/victim resource IDs, VM UUIDs, configuration revisions, Job/lease generation and operation generation before a subprocess runs. The intent blocks new Job reservations, configuration changes and conflicting power operations on the victim. The target claim is tied to that victim: the victim continues to count until its stop is observed; only then may the target start consume the transferred place. A pending start and an uncertain start or stop each count conservatively, so concurrent starts cannot spend the same place. No SQLite transaction spans `utmctl`.
- On restart or a stale response, reconcile the exact command intent against observed `utmctl` state and recorded identities before clearing protection. A revision mismatch cannot undo a command already issued. If stop issuance or its effect is uncertain, keep the victim protected and the target unstarted; do not retry blindly. A confirmed no-effect prerequisite failure follows the existing INCOMPLETE/no-start path. If no eligible victim exists before reservation, the requesting Job remains queued under its original queue deadline; inspect/events report `host_capacity_no_eligible_victim` and whether policy, pause, occupation, transition, unknown idle time or uncertain power blocks progress. Raise the limit only to the bound observed in TASK-016.
- A framework VM-limit error without a guest start is a temporary prerequisite gap, not quarantine. The affected job finishes INCOMPLETE. The controller pauses every `utm-macos` resource on this host with reason `host_vm_limit`, so queued VM jobs wait instead of failing one after another. The operator resumes the resources after freeing host capacity.

The TASK-013 host adapter additionally persists a command-return requirement with each effect claim. Until its claimant records a successful return, neither another caller nor restart reconciliation can advance that claim from power status alone. A successful return must still be paired with fresh identity-bound power observation; the next effect begins without the prior proof. A failed or unrecorded return remains protected for qualified reconciliation/recovery in TASK-015, and is never retried automatically. This uses the existing progress record and stages, without changing schema 9.

**DHCP lease validity and guest identity.** Select exactly one entry for the registered MAC from the supported host lease source. Its individual expiry must be known and later than the current time, whether the entry was written before or after the current VM start. An unexpired pre-start entry may be used only after the registered VM is observed started and the connection proves the pinned SSH host key, guest MAC, current boot identity and fresh run nonce. A lease-file modification time is not proof of an individual entry's freshness; an entry creation time is not assumed available. Recheck expiry and identity on renewal and after restart. Missing, ambiguous or unparseable entry/expiry, or failed identity checks, is a prerequisite gap; do not try another address-discovery mechanism.

**VM unavailable.** An unknown UUID, a `status` other than `started` or `stopped`, a proven failed start, no valid DHCP lease or failed guest identity check can be a prerequisite gap for one exact registered VM. When preparation has no owned Job effect requiring cleanup and every associated power operation is reconciled, durably pause only that resource with reason `vm_unavailable` before returning its reserved capacity; its Job settles INCOMPLETE with `cleanup_outcome=not_needed`. Reservation alone does not require Job-file cleanup. A confirmed, reconciled VM start before guest staging may also leave Job cleanup `not_needed`; a start or stop with uncertain effects cannot. Other VMs and local resources retain their availability and may progress. A failure after possible guest effects follows collection, cleanup or reconciliation instead. An older observation cannot pause a newer registration or replace an existing quarantine. The operator fixes the VM or its registration and explicitly resumes the resource after revision-bound readiness verification. Host-wide session, permission and framework-capacity failures retain their host-wide handling.

The adapter binds the registered UTM VM UUID, MAC address, pinned SSH host key, boot nonce and guest job root. A name or IP address alone is not VM identity. The MAC address is operator-asserted at registration, read from the VM's network settings in UTM, because `utmctl` does not report it; Haepari confirms it indirectly at every Prepare, when a current lease for that MAC must lead to a host with the pinned SSH host key. The address comes from the host DHCP lease table, looked up by the registered MAC address. `utmctl ip-address` is not used, because the Apple backend has no guest agent. The boot identity distinguishes boots; a fresh run nonce fences requests. No beta upgrade is a default prerequisite.

TASK-012 defines the native receipt required-field/default compatibility decision in the [F1 record](../records/TASK-012-managed-core-freeze.md). Only optional `log_limit_bytes` and exit `log` are newly omitted for historical compatibility; emitted required zero-valued identity and scalar fields retain their exact spelling and type.

## Explicit guest-attested evidence recovery

A finished retained VM Job whose immutable native exit has `termination_proven=false` cannot use ordinary guest file or cleanup operations. `resource recover --plan --action attest-guest-stopped` exposes a separate capability; it never upgrades that exit, adopts the old controller attestation, changes the terminal Job result or admits evidence-loss disposal. The resource must be quarantined with zero occupancy, no unresolved adapter intent and exactly one unresolved retained Job for this scoped operator statement. Failed observation, live ownership, a held control/run lock, changed original evidence or an unsupported recovery binary yields unknowns and no plan token.

The separate closed-shape `haepari.guest-recovery-request/v1` and `haepari.guest-recovery-reply/v1` use `runner guest-recovery --stdio`. Ordinary guest/request/exit/control shapes are unchanged. The same fixed bootstrap, dedicated strict SSH pin, mapping digest, fresh individual lease and native MAC/platform/boot challenge checks apply. The recovery executable is transferred with its own verified digest. The original per-Job executable and its digest remain frozen; a later controller must use the recorded recovery executable for replay.

A plan binds the resource and result revisions, complete original native request, Job/run/config/lease/nonce, guest boot, directory and control inode, and digests of `guest.json`, request, intent, start, outcome, exit and the legacy executable. The two-minute plan token also binds the recovery executable digest. Applying it requires fresh `operator-attested` evidence whose mechanism is `guest-workload-and-descendants-stopped`, reference is `job:<original-job-id>` and digest is the plan's guest recovery basis digest. The operator statement covers the full original workload and descendants; current PID absence alone cannot supply it. Its observation time must fall within the plan's authority window and not be in the future.

The host records a durable `attest-guest-stopped` evidence-recovery intent before issuing the guest effect, saving its permanent mutation key, original deadline, operator provenance and recovery executable. The host writes and syncs the complete recovery executable in a private temporary file before exclusive final-name publication and directory sync; replay never adopts an incomplete or different final file. Guest effects serialize under the original private single-link control inode and native run lock. Fresh native census rejects original supervisor/workload groups, sessions and visible descendants; unavailable census or a live filesystem owner blocks. Exact-existing immutable receipt replay completes the directory sync before subsequent effects, including interruption after exclusive publication. The guest publishes an immutable attestation outside the Job directory, then syncs the existing control's retirement flag to refuse delayed legacy prepare/start. A crash before that barrier leaves the attestation unusable until the exact saved operation is reconciled. Neither receipt is execution or termination proof. Hashing consumes the original deadline and each persistent attestation, retirement or cleanup effect rechecks that deadline after observation. A failed or expired uncertain operation preserves quarantine and all retained evidence; replay cannot extend its authority.

Only a matching completed host intent and guest attestation enable attested recollection. It revalidates the original root, receipts, executable, retirement barrier and current owners for each file operation. Required outputs retain the ordinary supplementary inventory; `GuestArtifacts` separately indexes the native log and six original JSON receipts in the sibling `<artifact_root>-native` directory. Required outputs retain their independent 1000-file/1 GiB budget; the native log uses the original request limit or historical 256 MiB default, and each of the six JSON receipts has its own 2 MiB bound. The durable recovery intent retains the original log limit; native evidence does not consume the required-output budget. Artifact delivery verifies the native inventory under its supplementary paths; a declared `guest_log_uncollected` gap may omit the absent original host log while the immutable result retains that gap. The existing owned bulk purge inventories this sibling directory and leaves attestation/control metadata intact. The log retains the original native request device/inode and, when present, the original exit manifest size/hash; changed or replaced logs refuse collection. Historical absent optional log manifests do not manufacture an original checksum. Collection failure preserves the guest directory. Durable collection and immediate verification of both inventories precede cleanup. The cleanup intent outside the guest Job binds the original attestation, collection inventory digest, saved cleanup key and deadline; deletion opens the bound original root and checks that FD against its expected device/inode before traversal, and a partial deletion never authorizes adoption of a replacement directory. Each file and final directory unlink rechecks the saved cleanup deadline after traversal and identity observations; expiry preserves the remaining source. Lost cleanup replies are reconciled by native health observation under the same deadline. A fresh, separately planned resource health action enables reuse only after resolved collection/cleanup and exact owned absence. The original terminal verdict, provenance and false native proof remain immutable.

This capability changes private recovery request/receipt payloads only. Existing public inspection and artifact supplementary responses retain a separate frozen v1 projection: attestation operations and their new private fields are omitted, while verified native files use the existing manifest file paths. Local recovery and historical payloads without the optional attestation or native supplementary inventory remain supported. Installation, real retained-Job recovery and installed-candidate VM qualification are separate operating decisions; local native fixtures and source review do not satisfy TASK-016/F2.

## EPIC-009 protocol decision (TASK-036)

Ordinary `haepari.guest-request/v2` / `haepari.guest-reply/v2` select positive output absence reporting for v2 Jobs. The reply's optional `absent` flag is valid only for a requested workspace file after exact-root validation and native termination proof; it carries no file or bytes. v1 exchanges preserve their previous payload and settlement semantics. Native guest stderr for both versions now contains only a classification code; v1 error envelopes retain their existing static messages, while v2 error messages use the code. A complete structured refusal may be classified despite a nonzero SSH exit, but never supplies effect or termination proof. Native execution receipts and original runner bindings remain unchanged.

Cross-boot operations use separate recovery v2 identities. Current recovery boot and original execution boot are distinct fields; original requests are not rewritten. Present native receipts and positively observed absence must form a verified predecessor inventory before recovery effects. Registered UUID/MAC, SSH pin, current lease, platform and exact owned root remain mandatory. A new boot proves cessation of processes on the old boot, never workload success. Every recovery apply is bound to its plan, mutation key and fixed deadlines.

Completed recovery authority and incomplete guest effects have separate replay rules. An exact saved attestation may be observed after its effect deadline only through a fresh read-only state check that verifies durable retirement. Publication without retirement cannot resume an expired effect. A committed host recovery intent may resume settlement after controller interruption only with that same original explicit authority and native completed proof; its host-only continuation does not renew the guest intent or any existing phase deadline. A present verified native outcome supplies its original workload outcome, exit code and signal when no host outcome is frozen. An already frozen host outcome takes precedence, including its cancellation classification. Importing receipts alone supplies no outcome projection and never changes their native termination flags.

A v2 guest control pins both the outer Job root and prepared workspace incarnation before start. Its optional `workspace_root` is required once guest-control/v2 publishes the native request and forbidden by v1. An interrupted prepare may have no workspace binding; an existing unbound directory is not adopted or deleted. V2 reboot recovery of a v2 guest request carries that original workspace binding in its basis and checks it again before evidence reads and cleanup. No current pathname is adopted as a replacement for a lost original directory.

Cross-boot supplementary recollection of a v2 Job uses separate `haepari.evidence-recovery-intent/v2` and `haepari.evidence-recovery-receipt/v2` when absence reporting is enabled. Its `absence_binding` pins the original workspace, original/recovery boots, attestation digest and original validated authority evidence. The native current-boot check and retired original control remain mandatory even when that original evidence is operator-attested. Each `absent_outputs` entry records a required path and its observation time inside the saved collection window. Verified artifact paths and absent paths form one unique, disjoint required-output inventory; native logs and present receipts have their separate verified inventory. V1 private intents and receipts reject these absence fields, including explicit null fields. Public v1 supplementary projections continue to omit private proof metadata. Collection does not rewrite the original terminal result.

Recovery/v2 may report positive absence only for the original guest/v2 workspace, with offset zero, no expected file and no returned file or bytes. Log and receipt requests retain their evidence gates. Cleanup binds absent paths into `haepari.guest-attested-cleanup/v2` as well as the host collection digest, original key and deadline; the native guest checks each path before publishing that intent and immediately before deletion under the original locks. A newly existing file blocks deletion. Cleanup without absent paths retains its v1 intent. A transport loss requires fresh native observation of completed deletion or stopped ownership; it never grants another effect budget.

Recovery/v2 also has a separate `completed_cleanup` read-only reply variant for an already completed ordinary cleanup. It opens the current private single-link control file without following symlinks, locks it and checks that its FD and current pathname refer to the same inode. It also requires the exact original request/root, stopped error-free completed cleanup, its valid native termination observation and fresh no-follow absence of the original Job pathname. The host has no historical control-inode pin. It contains no attestation or retained-root basis. Current registered identity, pin, lease and a different native boot still apply. The host requires the original collection and cleanup intents, stopped controller workers and reverified host files/logs before consuming this proof. It performs no workload or deletion. A late host completion observation retains the original cleanup deadline and INCOMPLETE classification; its separately recorded native authority can resolve the evidence hold and support a fresh resource-health plan without rewriting that result. Unknown or replaced roots, incomplete control, false native proof and uncollected or changed host evidence remain blocked.

TASK-036 preserves closed native refusal classifications through ordinary guest/v2 and recovery/v2 exchanges, including their preliminary pinned identity proof. Recovery/v2 probes identity with its trusted executable and supported guest/v2 request; the original nested guest request, runner and native receipts remain unchanged. A negative envelope after recovery issuance retains uncertain-effects classification and the native cause. Recovery/v1 retains static error messages. Arbitrary error text, stderr and payloads never become diagnostic codes; no classification authorizes cessation, cleanup or another effect.

## TASK-037 readiness and owned transport capability

A cold preparation waits for a successfully returned original start command to
be observed as started, a unique current registered-MAC lease, and pinned guest
identity, inside the original prepare deadline. Polling uses bounded backoff and
rechecks cancellation, configuration, lease/slot and controller ownership before
claiming a guest run. An uncertain or failed power command is never reissued or
resolved by this polling. Permission denial retains the host-wide pause path;
VM-local pre-claim failure retains its no-effect pause. A pre-claim cancellation
can settle only with no run, native receipt, effect or unresolved power intent.
If cancellation and host denial coincide, cancellation preserves the verdict
while the same fenced classification still pauses available host VM resources.

Apple bootpd's Ethernet host-identifier writer uses hexadecimal octets without
zero padding ([S16](../sources.md)). DHCP Ethernet entries therefore accept six
one- or two-digit hex octets and normalize them to the registered strict MAC.
Registration and guest identity syntax are unchanged. Multiple matching entries,
including padded/unpadded aliases, non-Ethernet identifiers, malformed octets
and individually expired leases refuse; there is no alternative address search.

[ADR-0019](../architecture-decision-records/0019-owned-runner-transport.md) selects
a distinct closed `guest-transport-request/reply/binding/v1` capability around
unchanged guest v1/v2. New controller admissions save a separate immutable
`haepari.vm-transport-admission/v1` event before preparation. Prepared native
control returns an exact root and private single-link runner incarnation; that
binding is retained outside event-prefix pruning. Compact exchanges carry three
fixed files (request, digest and encoded owned identity), copy the original
no-follow runner into private scratch, check SHA-256 and repeat native root/file
identity checks. Equal bytes at a replacement inode refuse. An interrupted
compact call never falls back to a second issued effect. The preliminary pinned
identity exchange remains separate; log/file pages remain at most 64 KiB with
original file metadata and offsets.

Historical Jobs without the admission marker continue the original full
bootstrap against their original executable, even when the current controller
supports the capability. A capable admission with interrupted preparation uses
the full new bootstrap until its binding is proven. No historical native request,
control, result, token or schema identifier is rewritten. A separately pinned
current verifier may perform only completed-cleanup read-only health, including
original attested recovery health, preserving the original runner/recovery
identity, native termination and outside control/attestation. It cannot perform
replacement-byte workload, collection or cleanup. Root presence blocks this
post-cleanup verifier path.

SSHRunner measurements record versioned start/completion pairs with exact
Job/run/VM identity, request/executor digest, original deadline, UTC start,
application archive/executable bytes, drained stdout/stderr bytes, elapsed call
time, exit and transport failure. Start is durable before issuance; failed
completion publication leaves a measurement gap and never reissues the call.
At 4096 admitted exchanges, one explicit detail-limit gap stops new details;
missing pairs and gaps cannot establish totals. These are application bytes at
the SSH subprocess boundary, excluding SSH packet overhead and throughput.

Explicit finished-Job purge inventories known host `guest-runner` and exact
attested `guest-recovery-runner-<digest>` payloads. Before an intent it requires
private regular single-link no-follow bytes matching the saved digest; the intent
then pins their current device/inode and replay refuses replacement. Unknown
final runner leaves refuse. Unpublished `.guest-recovery-runner-*` temporaries
have no final-path authority and remain outside the deletion inventory, with
their bytes retained even when known final payload purge succeeds. Active, occupied, quarantined, recovering or unresolved
Jobs retain payloads. Old admission/mutation keys, native bindings, required
receipts and frozen results remain retained; no automatic expiry is added.
The host does not claim a historical payload-inode pin before purge intent.
