# Haepari implementation prompt

Implement Haepari v0.1.0 from this package in its own repository. Read README.md, requirements.md, architecture.md, the ADR index, the active contracts (cli-and-jobs, resource-and-runner, artifact-and-profile, managed-transitions, configuration and locks), operations.md, verification.md, traceability.md and roadmap.md before changing code. Read the deferred external contract and integrations/mulgae-review.md only for scope context. Read applicable repository guidance and preserve unrelated work.

Use Go for the independent CLI, daemon and transient runner. Follow the roadmap's recommended task order and actual prerequisites. The original 32 task IDs remain stable; Haepari:TASK-033 adds the first integrated local slice, Haepari:TASK-034 adds the early UTM probe, Haepari:TASK-035 adds advisory named locks (ADR-0017), and Haepari:TASK-029–032 remain deferred. Execution order is not numeric across epics. When only a hardware gate blocks an epic, continue with later tasks whose prerequisites are met. Each task is intended to produce one reviewed implementation commit under the actual approved execution envelope. Do not mark a task complete from compilation, mocked UTM behavior, a command exit code or an unobserved manual check alone.

Maintain the core invariants: immutable admission; same-key recovery without duplicate launch; resource ownership through collection and cleanup; no replay of uncertain managed execution; complete installation-unit identity including skills; real prior-state migration; fresh-session skill evidence; truthful manual results; and a stable controller independent of every product under test.

Keep project tests and migration recipes in their owning repositories. Implement common resource/UTM/SSH contracts and sample fixtures, not product-specific branches or another general workflow engine. Do not introduce a mandatory integration-test repository, public network service, distributed scheduler, or required MCP server.

Do not install or replace real host tools, enable services, operate unregistered VMs, copy authentication, invoke providers, send Sorage messages, delete aquarium-dev state or publish releases without the applicable explicit authority. Missing real-environment prerequisites must be reported and must block the corresponding acceptance claim, not be worked around with a host install or successful skip.

At each task handoff, report exact changed files, checks and outcomes, relevant candidate/artifact identities, remaining evidence gaps and the next canonical task. The final handoff must satisfy handoffs/haepari-to-aquarium.md. Aquarium adoption is downstream work and must not be required to complete Haepari's producer implementation.

Design Revision 3 implements managed local and UTM macOS execution only. Use the first production-path local walking skeleton in Haepari:TASK-033, then harden the same path. Keep public schemas provisional until freeze gates F1 (TASK-012), F2 (TASK-016) and F3 (TASK-020). Confirm TASK-001's bootstrap decisions (module path, license, AGENTS.md, Make targets) with the owner before the first commit. Implement the [managed transition table](../contracts/managed-transitions.md), nested acquisition rejection, fenced operator recovery and job cleanup on the persistent VM ([ADR-0018](../architecture-decision-records/0018-persistent-vm-no-reset.md)). Qualify UTM in a real authorized environment before claiming the backend. EPIC-008, external APIs, E01–E20 and Linux runtime qualification are deferred. Do not claim an upgrade from a nonexistent public Haepari predecessor.
