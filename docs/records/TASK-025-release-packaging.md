# TASK-025 release packaging decision record

Effective with TASK-025 implementation; acceptance belongs to the [canonical roadmap](../roadmap.md). This record captures the packaging, release-service and paired-skill decisions and their verification boundary. It freezes no artifact identity: the release candidate is unpublished, and exact archive/binary/skill digests are bound later by the explicitly observed candidate (TASK-027), never retroactively here.

## Decisions

| Decision | Content | Owner |
| --- | --- | --- |
| Version stamping | `internal/identity.Version` stays `0.1.0-dev` for ordinary `make build`; `build/build.sh <output> <version>` adds only the `-X` stamp through the existing signing/link path (small approved shared-helper change; both paths verified). `build/release.sh` assembles the package under a fresh output directory and honors caller `TMPDIR` for packaging scratch. | `build/build.sh`, `build/release.sh`, `Makefile` (`release`) |
| Package layout | One top-level `haepari-<version>-darwin-arm64/` tree: version-stamped `haepari`, `SHA256SUMS` (every file except itself), basename-relative archive sidecar binding the whole archive, packaged `verify_tree.py`, `INSTALL.md`, unchanged MIT `LICENSE`, `skill/use-haepari/SKILL.md`, exercised examples. `dist/` is ignored. | `build/release.sh`, `packaging/` |
| Complete-tree verification | `packaging/verify_tree.py` (standard library, independent of the product binary) reports each missing, added or tampered entry against `SHA256SUMS` without following symlinks: unlisted symlinks/special files are added, a recorded regular file replaced by a symlink, special file or directory is tampered even with identical target bytes, and `SHA256SUMS` itself must be regular; ordinary structural directories stay unlisted without complaint. Plain `shasum -c` cannot detect extra files and is documented as insufficient alone. The qualification harness cross-checks with its own independent inventory, including dangling-symlink and symlink-replacement negatives. | `packaging/verify_tree.py`, [TESTING.md](../../TESTING.md) |
| Release service plan | Additive `haepari.release-service-plan/v1` with label `io.rootkernel.haepari.<instance>` and owner marker `haepari.release-service-owner/v1`, planned by `service plan --release` and installed/removed through the existing `--plan-file` path. Guards, Aqua/`AbandonProcessGroup` supervision (TASK-004), digest pinning, default-root refusal, occupied-uninstall refusal and state preservation are reused unchanged from the development lifecycle; limits are always serialized in the exact daemon argv (defaults 1/1); the plan file is the response `data` object, not the envelope. Development plan v1/v2 shapes are byte-compatible and regression-pinned. | [CLI and jobs](../contracts/cli-and-jobs.md), `cmd/haepari/service.go` |
| Frozen-help boundary | Machine-readable help is frozen at F1; release services were outside F1's frozen scope. The surface adds exactly one append-only `haepari.help/v1` synopsis entry (`service plan --release`) with existing structure and entries unchanged, following the TASK-023 recorded-delta precedent; the plan schema is a separate recorded decision. This is a targeted addition, not a blanket exemption. | [F1 decision](TASK-012-managed-core-freeze.md), [CLI and jobs](../contracts/cli-and-jobs.md) |
| Capability freeze semantics | `version`/`capabilities`/`help` output shapes are unchanged. The frozen capability fact is the captured output bound to the package digest; `compiled_backends` reports only the bootstrap backend (`local`), distinct from resource kinds, and `qualified_backends` stays empty until real backend qualification is recorded as a separate digest-bound record (TASK-027). No later qualification rewrites this package's frozen output. | `cmd/haepari/main.go`, `internal/platform`, `internal/managed/capabilities.go` |
| Paired skill | `skill/use-haepari/SKILL.md` (single self-contained file) teaches capability checking, scoped authorization, submit-once with a persisted request key, blocking wait and same-ID reconnection, truthful verdicts and error-code/retry handling, cancel with the actual immutable final verdict (a known earlier FAIL/INCOMPLETE is never rewritten), recovery basics, the advisory-lock owner/borrower flow — including owner cleanup of an abandoned queued request (`lock cancel <request-id> --json`, request-ID recovery through a same-key no-`--wait` acquire replay, wait timeout never treated as cancellation) and read-only borrower validation through public `locks list` paging with same-page deadline comparison, where CONFLICT/LOCK_EXPIRED/NOT_FOUND are consumer validation outcomes rather than automatic CLI errors — with mandatory `--json`, nested prohibitions and the release boundaries. Its tree identity is the SHA256SUMS entry; discovery/behavior grading stays consumer-optional. | `skill/use-haepari/SKILL.md` |
| Portable examples | Two ready resource examples plus auto/manual job examples carrying only the clearly marked `<BUNDLE_ROOT>`/`<TREE_SHA256>` placeholders, rejected by the product validators until localized; `INSTALL.md` documents the public `haepari-tree-sha256/v1` regeneration step. No unmarked executable placeholders ship. | `packaging/examples`, `packaging/INSTALL.md` |

## Verification and limits

The explicit installed release-package check in [TESTING.md](../../TESTING.md) owns the observation: one unique `h7-t25-rel-<scenario>` instance under a test-owned scoped HOME, baseline audit before install and final audit after uninstall, TERM/KILL reattachment with unchanged original identity/deadline and one workload effect, the native flow matrix, refusal guards and state-preserving uninstall. Its bounded audit limits (scoped-HOME completeness, allowlisted Haepari-owned `Library/LaunchAgents` parents, read-only non-secret real-host sentinels, no whole-host tracing, no causal attribution) are operator guidance in [operations](../operations.md).

Observed during implementation: the focused unit specs `Task025ReleaseServicePlan`/`Task011DevelopmentServicePlan` passed (9 selected specs, race detector on), and the packaging scripts, harness and paired skill passed syntax/frontmatter checks. The explicit installed-package check passed on macOS arm64: pristine inventory plus missing/added/tampered negatives, independent execution, localized examples, same-key replay/conflict, timeout/reconnection, synthetic manual PASS and unobserved-INCOMPLETE, queued cancellation, lock owner/borrower handling, both TERM/KILL reattachments and verified cleanup. Uninstall preserved state before harness-owned cleanup; the scoped-HOME audit and enumerated real-host sentinels had no unexpected final differences. The archive sidecar also verified after moving it with the archive. Exact commands, artifact identities and outputs remain private runtime evidence. Synthetic manual records exercise the interface; TASK-027 still requires an ordinary observed manual scenario. The common gate is run separately through `make test`; its current result is retained with the exact candidate evidence. No live VM, stable/default service, publication or host toolchain effect is claimed.

TASK-026 owns the broader documentation reconciliation; TASK-027 re-verifies the exact packaged candidate and records backend qualification separately.
